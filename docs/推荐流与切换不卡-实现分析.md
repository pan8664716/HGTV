## 0. 摘要

| 问题 | 结论 |
| --- | --- |
| 打开应用怎么取推荐 | 冷启动 → `openRecommend()` → 分类落地页接口 `POST /reading/distribution/category/landpage/v/`（`genre=[]`、不传 `sort`、`offset=0`、`limit=20`、`session_id=""`）→ `data.video_data[]` 即推荐列表 → 取第 1 部详情 → 取首集播放地址 → 起播 |
| 为什么每次都一样 | 请求里**没有任何续流 / 个性化 / 曝光状态**：`session_id` 恒为空、`offset` 每次归零、第 3 页起固定回落 `hot_score` 榜单、且从不回传曝光与行为。服务端视角永远是「一台设备第一次打开推荐页」 |
| 为什么切换不卡 | 七层叠加：会话级列表缓存 → 相邻两部详情预热 → 相邻两部「首集地址 + 前 1MB」预热 → 复用同一个 ExoPlayer 实例（不 stop / 不重建 View）→ 无感换源路径 → 黑场过渡遮住换源瞬间 → 令牌机制防串台 |

一句话：**列表侧是「无状态请求 + 客户端假装换了」，播放侧是「预取 + 复用 + 遮盖」，两者互不相关，要分开改。**

## 2. 打开应用后的完整链路

### 2.1 时序

```
Application 启动
   │
   ├─ MainActivity.onCreate：建 root、library、artwork、PlaybackTransport…
   │
   ├─ library.loadAsync()  ── 读本机记录（native-library-v1）
   │        │
   │        └─ onSuccess：
   │             applySessionToken() / applyAccount()
   │             SessionBootstrap.onAppStart()        ← 会话心跳
   │             if (launchRecommendPending) openRecommend()
   │
   ├─ MainActivity.onResume：
   │        if (library.isLoaded && initialCatalogPending) openRecommend()
   │
   ▼
openRecommend()
   ├─ resume = recommendItems.isNotEmpty()      // 会话级缓存
   ├─ screen = "recommend"
   ├─ if (resume) → playRecommendAt(recommendIndex)   // 不发列表请求
   └─ else：
        recommendItems = emptyList(); recommendPage = 0
        loadRecommendPage(append=false) { playRecommendAt(0) }
             │
             ├─ registerDeviceOnce()（未注册时）
             ├─ repository.categoryFeed(CategorySelection(), 1, needPanel=false)
             │      └─ POST /reading/distribution/category/landpage/v/
             │           body: offset=0, limit=20, select_items={genre:[]},
             │                 session_id="", req_type="only_content"
             │
             └─ onSuccess → recommendItems = video_data[]
                             → playRecommendAt(0)
                                   │
                                   ├─ recommendDetails 命中？→ 直接起播
                                   └─ 否则 repository.detail(series_id)
                                          └─ POST /novel/player/video_detail/v1/
                                                 → video_list[]（vid = 分集 ID）
                                                 → startRecommendEpisode()
                                                       │
                                                       ├─ recommendPrepared 命中？→ 直接用
                                                       └─ 否则 repository.stream(vid, maxQuality)
                                                              → RemoteVideo.prepare()
                                                              → ProgressiveMediaSource
                                                              → 首帧上屏
```

### 2.2 两个入口标记

| 标记 | 位置 | 语义 |
| --- | --- | --- |
| `launchRecommendPending` | `MainActivity.kt:774` | 本机记录**第一次**读起来时消费一次，之后返回首页不再自动跳推荐 |
| `initialCatalogPending` | `MainActivity.kt:248` | `onResume` 首次进入时消费一次，防止从后台回来被反复拽进推荐页 |

`openRecommend()` 内部还有幂等守卫（`MainActivityRecommend.kt:48`）：已在推荐页且列表非空 / 请求在途时直接返回，所以两个入口同时触发不会重复起播。

### 2.3 会话级缓存与「进程重启」

`recommendItems` 是 Activity 字段，不落盘：

- **同一进程内**再次进推荐 → `resume == true` → 零网络、续播上次那一部；
- **进程被杀 / 冷启动** → `recommendItems` 为空 → 必然重新拉第 1 页；
- 从推荐返回首页（`goHomeFromRecommend`，`:656`）**不清** `recommendItems`，只清预热缓存（`closeRecommendCache`）。

> 这就是「我明明退出去又进来，还是那一批」的直接原因之一：进程内的缓存设计成连续的，进程重启后又从同一个起点重新拉。

## 3. 推荐接口协议（现状）

### 3.1 请求

```
POST https://api5-normal-sinfonlineb.fqnovel.com/reading/distribution/category/landpage/v/?<设备参数 + ts/_rticket + 签名>
Content-Type: application/json; charset=utf-8
```

请求体（`ContentRepository.kt:898`）：

```json
{
  "filter_ids": "",
  "req_scene": "default",
  "offset": 0,
  "limit": 20,
  "need_selector_panel": false,
  "select_items": { "genre": [] },
  "session_id": "",
  "req_type": "only_content",
  "client_req_type": 3
}
```

要点：

| 字段 | 现状 | 说明 |
| --- | --- | --- |
| `select_items.genre` | `[]` | 空数组 = 全站综合（不筛体裁） |
| `select_items.sort` | **不传** | 不传 = 服务端自己的「推荐序」；传 `hot_score` / `hot_collect` / `online_time` 即变成对应榜单 |
| `offset` / `limit` | 0 / 20 | 第 1 页 20 条；第 2 页起 `limit=100` |
| `session_id` | `""` | **恒为空**，服务端无法识别「同一条流的续页」 |
| `req_type` | `only_content` | 只回内容，不要筛选面板 |
| `client_req_type` | `3` | 与官方 App 对齐 |

签名与身份：

- `categoryApiRaw()`（`:964`）每次重试都重新签名（`ts` / `_rticket` 属于签名输入，复用旧签名会被判过期）；
- 必须同时有 `x-medusa` 与 `x-helios`，缺一个就回 `HTTP 200 + Content-Length: 0`；
- `withSession()` 附设备 Cookie（`install_id` / `ttreq` / `store-region`）或账号 Cookie；
- 设备身份必须是**平台注册过**的那一份（`registerDeviceOnce()` 先跑）。

### 3.2 响应

```json
{
  "code": 0,
  "data": {
    "has_more": true,
    "next_offset": 20,
    "session_id": "……",
    "video_data": [
      {
        "series_id": "……",
        "title": "……",
        "cover": "……",
        "video_desc": "……",
        "episode_cnt": 86,
        "copyright": "……",
        "recommend_info": { "rank": "1" },
        "recommend_reason_list": "{\"sub_title_list\":[{\"content\":\"9014万\",\"data_type\":27}]}"
      }
    ]
  }
}
```

`apiCard()`（`:1015`）只取 `series_id` / `title` / `cover` / `video_desc` / `episode_cnt` / `copyright`，**`next_offset` 与 `session_id` 被丢弃**。

### 3.3 分页映射（关键）

`categoryOffset()`（`:919`）对「全部推荐」（`sort == null` 且无细分筛选）：

| 逻辑页 | `offset` | `limit` | `sort` | 实际内容 |
| --- | --- | --- | --- | --- |
| 1 | 0 | 20 | 不传 | 推荐流前 20 条 |
| 2 | 20 | 100 | 不传 | 推荐流剩余约 80 条（到 100 条后 `has_more=false`） |
| 3 | 0 | 100 | `hot_score` | **热播榜前 100 条** |
| 4 | 100 | 100 | `hot_score` | 热播榜第 101–200 条 |
| … | … | … | `hot_score` | … |

`categoryApi()` 里 `more` 的计算（`:914`）：

```kotlin
val more = (serverMore || (recommendation && page <= 2)) && page < MAX_CATALOG_PAGE
```

也就是说第 2 页即使服务端回 `has_more=false` 也会继续翻，从第 3 页起改走热播榜。界面侧 `loadRecommendPage` 最多翻到第 10 页（`page > 10` 直接回调）。

## 4. 为什么每次显示一样的推荐

### 4.1 成因一：请求没有任何「续流状态」（主因）

原版 App 的推荐请求模型是 `BookstoreTabRequest`（反编译产物 `com/dragon/read/rpc/model/BookstoreTabRequest.java`），其中与「换一批」直接相关的字段：

```
session_id / session_uuid                 流游标
offset / next_offset                      续流位置
recent_impr_gid                           最近曝光内容
last_view_series_id                       上一部看的
recommend_extra / refresh_action_info     刷新意图
video_tab_cold_start / is_video_feed_tab_first_request_cold_start
last_session_video_tab_type / tab_version
```

我们的请求：

```json
"session_id": ""
```

其余字段一个都不传。对服务端而言，**每一次请求都等价于「一台全新设备第一次打开推荐页」**，返回的自然是同一套默认排序。

### 4.2 成因二：每次冷启动都从 `offset=0` 重来

`openRecommend()` 的非 resume 分支（`:71`）：

```kotlin
recommendItems=emptyList(); recommendIndex=0; recommendPage=0; recommendHasMore=true
```

进程重启 → 必然走这条 → 永远取 `offset=0, limit=20` 的那 20 条。同一设备身份、同一区域、同一时段下，这 20 条是稳定的。

### 4.3 成因三：第 3 页起固定回落热播榜

见 §3.3。推荐流本身只到 100 条，之后全部是 `hot_score` 榜单：

- 榜单排序由热度决定，短期不变；
- 与推荐流前 100 条大量重叠；
- 界面 `distinctBy { it.id }` 一过滤，新增可能只有个位数。

结果：整条流实际可用条目约 100 部，且顺序确定。

### 4.4 成因四：零反馈回传

原版有 `POST /reading/distribution/recommend_stat/report/v1/`，上报 `StatData`：

```
recommend_info     列表项里的 recommend_info 原文
group_id           内容 ID
candidate_data_type / content_type / show_type / stat_item_type
client_time
```

（见 `/Users/star/Downloads/hongguo/artifacts/jadx_out/sources/com/dragon/read/kmp/recommend/KmpShortVideoRecommendStatReporter.java`）

我们既不上报曝光，也不上报「划走 / 看完 / 点击」，服务端拿不到任何调整下一批的依据。

### 4.5 次因：会话内「续播」而非「换一批」

`openRecommend()` 的 `resume` 分支 + `goHomeFromRecommend()` 不清列表，是**有意的连续流设计**（保证上下切换不断档）。但用户感知是「还是这些」。要区分两件事：

- **同一次运行内**：应当连续（这是对的，不要改）；
- **跨进程 / 跨天**：应当换一批（这是缺的）。

## 5. 上下切换不卡的七层实现

### 5.1 总览

```
按键 DOWN
  │
  ├─ ① showRecommendCover()          画面淡黑（120ms，纯 View，不依赖 Surface）
  ├─ ② switchRecommend(1)            只改索引，不拉列表
  ├─ ③ playRecommendAt(next)
  │     ├─ recommendDetails 命中 → 直接拿 Detail（零网络）
  │     └─ 否则 pause + 取详情（几百 ms，黑场盖住）
  ├─ ④ startRecommendEpisode()
  │     └─ recommendPrepared 命中 → 拿到已 prepare + 前 1MB 的 RemoteVideo
  ├─ ⑤ playEpisode(prepared=…)
  │     ├─ reuse = 播放器与 PlayerView 都在 → 不重建整棵树
  │     └─ seamless = reuse && prepared != null → 不 stop / 不 clearMediaItems
  ├─ ⑥ onRenderedFirstFrame → revealRecommendCover()（260ms 淡出）
  └─ ⑦ 令牌校验：旧请求 / 旧回调一律丢弃
```

### 5.2 第 1 层：列表不重拉

`switchRecommend()`（`MainActivityRecommend.kt:529`）：

```kotlin
val next = from + direction
when {
    next in recommendItems.indices -> playRecommendAt(next, 0L, direction)
    direction > 0 && recommendHasMore -> loadRecommendPage(true) { … }   // 到末尾才补页
    else -> playRecommendAt(if (direction > 0) 0 else recommendItems.lastIndex, …)  // 环绕
}
```

- 上下切换**不发列表请求**；
- 到末尾才补一页；补页失败 / 无更多则环绕回第 1 部，不会「按了没反应」。

### 5.3 第 2 层：相邻两部「详情」预热

`prefetchRecommendNeighbors(index)`（`:293`）在起播之后立即执行：

```kotlin
listOf(index + 1, index - 1).forEach { i ->
    val cached = recommendDetails[series.id]
    if (cached != null) { warmRecommendDetail(cached); return@forEach }
    io.submit { repository.detail(series.id) }   // 结果进 recommendDetails
}
```

- 缓存：`recommendDetails` 是 LRU，容量 6（`MainActivity.kt:782`）；
- 去重：`recommendDetailLoading` 防止同一部被连按重复请求；
- 落地条件：仍在推荐页即可（**不认起播令牌**，因为它是为「下一次切换」准备的）；
- 只有当它仍挨着当前这一部（`position - recommendIndex in -1..1`）才继续做流预热。

于是按下键时 `playRecommendAt` 里这条早退命中：

```kotlin
val cached = recommendDetails[series.id]
if (cached != null) { startRecommendEpisode(cached, position, autoplay); return }
```

### 5.4 第 3 层：相邻两部「首集流」预热

`warmRecommendDetail()`（`:323`）：

```kotlin
val prepared = RemoteVideo(http, source.stream(episode, quality)).also { it.warm() }
recommendPrepared[key] = prepared        // key = "vid:清晰度"
```

`RemoteVideo.warm()`（`RemoteVideo.kt:49`）：

```kotlin
prepare()                                        // Range 0..256KB，解析 MP4 头 / 样本索引 / 派生 AES key
if (prefix.size < size) prefix += range(...)     // 补到前 1MB
```

也就是说，命中缓存时**播放地址、moov、样本索引、首批媒体字节都已经在内存里**，起播不需要再走网络。

约束（都是刻意的）：

| 约束 | 代码 | 原因 |
| --- | --- | --- |
| 同一时刻只预热 1 部 | `if (recommendWarming.isNotEmpty()) return` | 两条流同时拉会互相抢带宽，反而都慢 |
| 下一部优先 | `listOf(index+1, index-1)` | 用户往下刷的概率远高于往回 |
| 只留最近 3 部 | `while (recommendPrepared.size > 3)` | 每部约 1MB，再多没有意义 |
| 计费网络 / 无网不预热 | `if (connectivity.isMeteredConnection() || !networkAvailable()) return` | 省流量；代价是此时切换走慢路径 |
| 内存吃紧时释放 | `onTrimMemory` 里 `closeRecommendCache()` | 纯缓存，可重建 |

### 5.5 第 4 层：复用播放器，不重建 View

`playEpisode()`（`MainActivityPlayer.kt:265`）：

```kotlin
val reuse = (screen == "player" || recommendEntry) && player != null && playerView != null
            && !recovering && !playError
val seamless = reuse && prefetched != null
```

| 分支 | 行为 |
| --- | --- |
| `reuse == false` | `root.removeAllViews()`、新建 `PlayerView`、必要时 `ExoPlayer.Builder.build()` |
| `reuse == true` | 不重建整棵树；`playerListener` 重挂；`setMediaSource` 换源 |
| `seamless == true` | **不** `player.stop()`、**不** `clearMediaItems()`；旧一集资源延迟回收 |
| `seamless == false` | `stop()` + `clearMediaItems()`，但仍复用播放器实例与 View |

关键细节：

- `playerView?.player` 复用同一 Surface，避免 SurfaceView 重建造成的黑屏；
- 旧一集的 `RemoteVideo` / 传输不立刻关（`scheduleRetire()`，`MainActivityPlayback.kt:69`）：等新源 `READY` 或 3 秒兜底再 `retirePreviousEpisode()`，否则旧 period 还在读时会读到已关闭对象抛 `IOException`；
- 无感路径下调 `suppressBufferingUi()`（`:50`）：`SHOW_BUFFERING_NEVER`，1.2 秒后恢复，避免闪一下转圈。

### 5.6 第 5 层：黑场过渡

| 环节 | 代码 | 参数 |
| --- | --- | --- |
| 盖黑 | `showRecommendCover()`（`:375`） | 淡入 120ms（`COVER_IN_MS`） |
| 挂载位置 | `attachRecommendCoverView()` | 插在底部信息浮层**下面**，剧名/集数仍可见 |
| 揭开 | `revealRecommendCover()`（`:411`） | 淡出 260ms（`COVER_OUT_MS`） |
| 触发时机 | `onRenderedFirstFrame`（真正出帧） | 不是 `READY` |
| 兜底 1 | `READY` 后 400ms | 个别设备复用播放器时不再报首帧 |
| 兜底 2 | `COVER_MAX_MS = 2500ms` | 新源一直不出帧也不能永久黑屏 |

黑场是普通 `View`（不是 SurfaceView），alpha 动画在电视盒子上一定生效；盖住期间不参与焦点、不拦截按键（推荐页按键本来就由 `dispatchKeyEvent` 消化）。

效果：用户看到的是「暗 → 亮」，看不到旧画面按新比例被拉伸的那一帧。

### 5.7 第 6 层：令牌防串台

| 令牌 | 递增时机 | 作用 |
| --- | --- | --- |
| `recommendToken` | 每次切剧、进正片、退出 | 丢弃上一次在途的详情结果 |
| `recommendPageToken` | 每次取页、退出 | 丢弃上一次在途的列表结果 |
| `recommendWarmToken` | 取消预热 / 换目标 | 在途预热结果回来时自己 `close()`，不塞缓存 |
| `playbackSession` | 每次 `playEpisode` | 丢弃上一会话的播放器回调 |

快速连按上下键时，中间几部的详情 / 预热结果会被丢弃，不会出现「按了三下、画面跳回第二部」。

### 5.8 第 7 层：传输与缓冲参数

`MainActivityPlayer.kt:539`：

```kotlin
DefaultLoadControl.Builder()
    .setBufferDurationsMs(20000, 60000, 1000, 2000)   // min / max / 起播 / 重缓冲
    .setTargetBufferBytes(24 * 1024 * 1024)           // 约 110 秒最高码率
    .setPrioritizeTimeOverSizeThresholds(true)
```

`PlaybackTransport.kt:53`：

```kotlin

.connectionPool(ConnectionPool(4, 5, TimeUnit.MINUTES)) // 切集不关池

```

`VideoDataSource.read()` 一次取 1MB：`RemoteVideo.read()` 命中 `prefix` 时直接从内存解密返回，不产生网络往返。

### 5.9 失败路径（不会卡死）

- 详情取不到 / 无分集 → `skipRecommend()` 自动跳下一部；
- 连续跳过上限 `RECOMMEND_SKIP_LIMIT = 4`，超过就停在一句提示上（按确定重试）；
- 取地址被平台判为未注册（`101000` / 空响应）→ `healDeviceIdentity()` 重注册后按原位置重试一次；
- 播放器错误 → `playerFailure()` 带 1.5 秒互斥窗，避免同一次故障被两条路径重复处理。

### 5.10 「不卡」的代价与边界

| 场景 | 表现 |
| --- | --- |
| 命中详情 + 预热（常见） | 切换接近「换一帧」，黑场淡入淡出约 380ms |
| 只命中详情、未命中预热 | 需取地址 + 读索引 + 首包，黑场撑住，通常 0.5–1.5 秒 |
| 计费网络 / 无网 | 不预热，全部走慢路径 |
| 连按上下键 | 中间结果被令牌丢弃，只播最后停在的那一部 |
| 首次进入推荐页 | 无预热，等同「只命中详情」的慢路径 |

按优先级排列。**只做 1–3 是客户端侧「假装换了」，做 4 才是真的换。**

### 7.1 P0：把服务端游标用起来

### 7.2 P1：冷启动轮换起点

### 7.3 P1：跨启动去重（客户端兜底）

触发点：

| 事件 | 触发位置 | 语义 |
| --- | --- | --- |

### 7.5 P2：扩大可用池

### 7.6 P2：预热策略微调（可选）

| 想法 | 收益 | 代价 |
| --- | --- | --- |
| 预热 2 部（当前 1 部） | 连按两下也命中 | 抢带宽，可能拖慢当前这一部 |
| 预热第 2 集 | 「进正片后连播」更快 | 与 `maybePrefetch` 重复，收益低 |

建议：**先不动**。当前策略在「不抢带宽」和「命中率」之间已经取到平衡；要动先做 §8 的命中率统计。

## 9. 风险与注意事项

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 服务端不接受 `offset` 起点 | 非 0 起点可能被忽略或回空 | 首次灰度只对 10% 启动生效；回空则退回 0 |
| `session_id` 与 `offset` 不匹配 | 游标跨页失效 | 每页落地即写回；失败重取时清空游标 |
| 去重把池子抽干 | recent 记了 200 条，池子只有 100 条 | 首屏过滤后若为空，清空 recent 重取一次 |
| 曝光上报被限流 | 高频上报触发风控 | 批量 + 5 秒节流 + 失败丢弃 |
| 预热抢带宽 | 当前只预热 1 部，已规避 | 不要轻易改成并发 2 部 |
| 黑场遮挡过长 | 新源一直不出帧 | `COVER_MAX_MS = 2500ms` 兜底已存在 |
| 令牌漏判 | 快速连按导致旧结果落地 | 所有异步回调都必须比对 `recommendToken` / `recommendPageToken` |
