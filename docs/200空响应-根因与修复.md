# 200 空响应：根因定位与修复（2026-11-11）

## 一、结论

**`200 + 空响应` 的唯一原因是 `x-medusa` 不正确，不是服务端风控。**

决定性字段是 medusa 内部的 **detection 位掩码**：仓库状态机用 `0x8000`
（`DetectionTypes = {15}`，protobuf field 10 / `Prefix = 00 80`），
官方 74332 稳定态是 **`0x8100`（`DetectionTypes = {8,15}`，`Prefix = 00 81`）**。
改成官方值后，同一台新设备连续 18 次请求全部成功，**0 个空响应**。

另有一处真机行为差异同时修正：状态机原先只在 `Initialize()` 取一次随机数，
导致后续每发请求的 `Nonce` / field 3 / Flags 低位完全重复；现改为每发重新取样。

**`x-gorgon` 的 20 字节负载不需要逆向。** 逐头消融证明：删掉 gorgon、
或把它换成我们未复现的本地负载，服务端都照常返回完整响应。上一轮把它列为
「必须重新逆向」是过度推断，本文档更正。

## 二、决定性证据

### 1. 官方六头 oracle（Frida 主动调用，安全）

`NetworkParams.tryAddSecurityFactor(url, headers)` 是 App 的 Java 签名入口，
被动抓包显示 **输入 11 个头 → 输出 6 个头**。用 frida CLI 在 App 内主动调用它
（不再调用 metasec native，避免 `libmetasec_ml.so` SIGSEGV），并让脚本用
`Date.now()` 同步构造 URL，得到「URL ↔ 官方六头」的严格配对。

关键约束：**输入头必须带与请求体一致的 `x-ss-stub`**。第一次未带 stub 时，
官方六头重放 3/3 全空；带上固定 gzip body 的 MD5 后，**连续 2/2 成功**
（20169 B、20119 B，`code=0`）。

### 2. 逐头消融（8 组官方 URL / 六头，每组换一个头）

| 组 | 操作 | 结果 |
| --- | --- | --- |
| a | 全官方（对照） | ✅ 20141 B |
| b | **去掉 `x-medusa`** | ❌ **空** |
| c | 去掉 `x-gorgon` | ✅ 20135 B |
| d | **`x-gorgon` → 本地未复现负载** | ✅ 20129 B |
| e | **`x-medusa` → 本地旧实现** | ❌ **空** |
| f | `x-ladon` → 本地 | ✅ 20133 B |
| g | `x-argus` → 本地 | ✅ 20211 B |
| h | `x-helios` → 本地 | ✅ 20201 B |

只有 medusa 一项决定成败；其余五头（含 gorgon 负载）服务端不校验或本地已正确。

> 注：本组实验里「去掉 medusa」是失败的（0/18 的 `no-medusa` 实验同样全空）。
> 之前观察到的「去掉 medusa 好像能响应」应属另一套接口/请求形态；在
> `/novel/player/*` 这组配置下，medusa 是必需且必须正确的。

### 3. 官方 8 组 medusa 解码后的推进规律（稳定态）

| 字段 | 官方表现 |
| --- | --- |
| `Nonce` / field 3 / Flags 低位 | **每发随机** |
| field 15 子字段 1 | 每发 +1（331→339） |
| `field 10` / `Prefix` | **恒定 `00 81`** |
| field 16 (token) | 恒定（同一进程稳定态） |
| field 15 子字段 2/3/5 | 恒定 |

修复前本地状态机：`Nonce`/field 3 恒定、`Prefix` 恒定 `00 80`。两处都偏离。

### 4. 归因实验矩阵（每组：全新 did，18 次请求，3 个不同 vid，单接口 9 次 + 批量 9 次）

| 实验 | 变更 | 成功 / 空响应 |
| --- | --- | --- |
| `baseline` | 原始实现 | 1 / 17 |
| `aligned` | 六头形态对齐真机 | 1 / 17 |
| `no-medusa` | 去掉 medusa | 0 / 18 |
| `reset-signer` | 每发重建 Signer | 1 / 17 |
| `replay-first` | 完全重放第一发（字节相同） | 1 / 17 |
| `no-jar` | 禁用 cookie jar | 1 / 17 |
| `random-rotated` | 修正 Random 复用 | 1 / 17 |
| **`detection-aligned`** | **+ detection `0x8000 → 0x8100`** | **18 / 0** |
| **`final-verified`** | **+ gorgon flag 统一 `00 81`** | **18 / 0** |

`replay-first` 说明问题不是「后续请求随机出错」，而是首发的签名被服务端接受、
后续签名不满足期望；`reset-signer`/`no-jar` 排除了状态累积与 Cookie 变化；
`random-rotated` 单独不足以解决，**detection 掩码是决定性变量**。

### 为什么没有把修复同步进 App 侧

`android/core/src/test/resources/signing.json` 是 **Android Kotlin、iOS Swift、
Go、Python 四端共享**的固定向量（内含 gorgon / helios / medusa 期望值）。
App 侧 `Signer.sign()` 目前用完整 Argus/Ladon 且**不带 `x-medusa`**，
其 medusa 实现是另一套旧协议结构，不存在 `DetectionTypes` 概念。
直接改 App 侧会同时：① 让四端向量测试失效；② 改变 App 线上请求形态，
而本轮真机样本只覆盖了工具侧构造的播放请求。

因此同步 App 侧应作为独立排期：先补抓 App 自身播放接口的完整请求，
再决定是移植 Go `sixheaders` 状态机还是只替换常量，随后统一重生成
`signing.json` 并跑四端向量 + 编译 debug。**本轮不仓促改动，避免破坏现网可用行为。**

### 其它边界

- 官方 oracle 目前用 App 自身设备身份；若要用于任意新 did 的批量压测，需确认
  medusa field 16 token 与 URL `device_id` 的一致性约束。
- 采样均为 gzip body 的 POST 视频模型接口；`x-ss-stub` 必须与实际 body 字节一致，
  否则即使六头正确也会返回空响应（本次已实测确认）。
