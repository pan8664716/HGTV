# HGTV 架构与性能评审

> 评审对象：HGTV 1.2.8（`com.hgtv.star`，versionCode 65）
> 评审日期：2026-10-29
> 评审视角：Android TV 音视频客户端（播放内核 / 网络 / 存储 / 遥控交互 / 工程化）
> 方法：全量静态阅读 57,032 行 Kotlin + 构建配置 + CI 配置；关键结论均给出文件与行号；可执行的结论已在本机实测。

---

## 一、结论摘要

**总体判断：这是一个"工程质量显著高于同类非官方客户端"的项目，但它的复杂度已经超过了单体 Activity 能承载的上限。**

具体表现在两个相反的方面：

- **做得好的部分是真做得好。** 基线 profile、首块 512KB 分片、DNS 落盘缓存、播放索引缓存、R8 剥日志、multidex 主 dex 保持、279 个单元测试、逐帧零测量的弹幕排版——这些不是"写了就算"的功能，每一条都对应着具体的实测数据（日志里的 `Stage ...`、`blankP50`、`took=139ms`）。多数商业客户端到不了这个细致程度。
- **但所有这些问题都被塞进了一个类。** `MainActivity` 及其 **22 个**扩展文件合计 **15,384 行**，持有 **297 个可写字段**，全部以 `internal` 暴露给彼此。没有 ViewModel、没有状态机、没有协程、没有依赖注入。当作者不得不用 `generation` / `playbackSession` / `playbackWatchdogSession` / `failureHandledSession` 四套"代际号"来手工防止异步回调串台时，问题已经不是"代码写得糙"，而是**架构缺少一个能表达"当前状态"的东西**。

**问题分级（按修复优先级）：**

| 级别 | 数量 | 性质 | 典型后果 |
| --- | --- | --- | --- |
| P0 | 4 | 安全 / 流水线阻断 / 明确缺陷 | 会话可被中间人截获；发版流程必失败 |
| P1 | 7 | 架构与资源 | 状态串台、写放大、进程死亡失忆、EOL 依赖 |
| P2 | 8 | 体验与工程化 | 手机可读性、无障碍、测试盲区、环境不可复现 |

**最需要立刻处理的三件事：**

1. **`SKIP_CERT_CHECK`**——Android 5.1 以下直接不校验证书链。这不是"老设备没办法"，因为**代码里已经内置了那张根证书**，做单锚校验在 API 19 上完全可行（`CertificateFactory` + `CertPathValidator` 都是 API 1 的接口）。
2. **发布流水线引用了一个不存在的测试类**——本机实测 `BUILD FAILED`，意味着自动发布链路当前是断的，Release 只能手工补。
3. **播放进度每 5 秒把 200 条历史全量序列化并 fsync**——播放一小时约 288MB 文件写入 + 720 次 fsync，而实际只需要 60 字节。

## 三、P0：立即修复

### P0-1 发布流水线必然失败（已实测）

**位置**：`.github/workflows/release.yml`，"校验元数据能被客户端解析" 步骤

```yaml
./android/gradlew -p android :core:test --tests 'com.hgtv.star.core.AppUpdatesTest' --console=plain
```

**事实**：全仓库搜索 `AppUpdates`，**0 命中**——这个类（连同它的测试）已经被删除，但流水线没跟着改。

**实测**（本机，JDK 17）：

```
> Task :core:test FAILED
* What went wrong:
Execution failed for task ':core:test'.
> No tests found for given includes: [com.hgtv.star.core.AppUpdatesTest](--tests filter)
BUILD FAILED in 914ms
```

**后果链**：

1. 该步骤位于 `assembleRelease` **之后**、`gh release create` **之前**；
2. Gradle 的 `--tests` 过滤无命中即失败，任务中断；
3. Release 不会创建，APK 只留在 workflow artifact 里；
4. 仓库根目录的 `HGTV_1.2.7.apk` / `HGTV_1.2.8.apk` 与 `tag v1.2.8` 说明发版是**手工补的**，`update.json` 生成后无人消费（README 也写明"应用内不提供更新入口"）。

**修复**：删除该步骤，或补回 `AppUpdates` + `AppUpdatesTest`。若确定放弃应用内更新，`update.json` 的生成也一并删掉——现在它是一份"看起来在维护、实际没人读"的产物，比没有更容易误导。

### P0-2 Android 5.1 以下完全跳过证书链校验

**位置**：`core/src/main/kotlin/com/hgtv/star/core/HgtvTls.kt:199`、`:289-301`

```kotlin
val SKIP_CERT_CHECK: Boolean = SDK_INT < 22
// ...
override fun checkServerTrusted(chain: Array<out X509Certificate>, authType: String) {
    if (reported.compareAndSet(false, true)) { NetLog.log("SDK $SDK_INT < 22：已跳过证书链校验 ...") }
}
```

**影响**：主机名校验（`OkHostnameVerifier`）仍在，但**证书链完全不验**。攻击者只要自签一张 CN/SAN 匹配 `api5-normal-sinfonlineb.fqnovel.com` 的证书即可完成中间人，无需任何可信 CA。而这个应用在这条链路上传输的是：

- 手机号 + 短信验证码登录流程（`PhoneLogin.kt`，1104 行）
- `sessionid` / `X-Tt-Token` / `TicketGuard` 签名（`PassportSigner.kt`）
- 账号收藏、历史、观看进度

**关键点在于这不是"没办法"**：同一文件 `:111-134` 已经内置了 `DigiCert Global Root G2` 的 PEM，`:168-174` 已经用它建好了 `EXTRA_TRUST_MANAGER`（单锚 PKIX 校验器）。也就是说，**严格校验所需的全部材料都在手上，只是对老设备选择了整段跳过**。

代码注释给出的理由是"这批设备没有再升级系统证书库的通道"——但内置单锚正是绕开系统根库的标准做法，且 `:222-230` 的严格分支已经在做"先验内置单锚、失败回退系统 PKIX"。把这条路直接复用给 API < 22 即可。

**修复方案（按推荐顺序）**：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A（推荐） | API < 22 也走 `EXTRA_TRUST_MANAGER` 单锚校验，失败即抛（fail-closed） | 需回归 4.4/5.0 真机；风险是旧 Conscrypt 的 PKIX 差异，可用"单锚失败 → 报错页"兜底 |
| B | 保持跳过，但**在跳过期间禁止登录**（只允许匿名浏览播放） | 功能降级，但凭证不外泄 |
| C | 只对内容接口跳过，对登录/账号接口强制单锚 | 折中，实现复杂 |

**不建议**保持现状。一个 TV 盒子上的短剧客户端持有用户手机号会话，把链校验关掉换取"少一类兼容问题"，风险收益不成立。

### P0-3 会话凭证明文落在公共存储

**位置**：`app/src/main/AndroidManifest.xml`（权限）+ `data/Library.kt:63-77`（`MIRROR_KEYS`）+ `data/SessionMirror.kt`

Manifest 里三条同时成立：

```xml
<uses-permission android:name="android.permission.WRITE_EXTERNAL_STORAGE"/>   <!-- 无 maxSdkVersion -->
<application android:requestLegacyExternalStorage="true" ...>                 <!-- targetSdk 29 下生效 -->
```

`MIRROR_KEYS` 明确包含：

```
"account-cookie", "session-token", "ts-sign", "x-tt-token", "registered-cookies", "last-beat-at"
```

这些被写进 `/sdcard/.hgtv/`。

**风险**：

1. **Android ≤ 9**：任何持有 `READ_EXTERNAL_STORAGE` 的应用都能读取该目录，直接接管账号会话；
2. **物理接触**：插上电脑即可拷走，无需 root；
3. **卸载不清理**：这是设计目标（重装免登录），但也意味着用户"卸载应用"后凭证仍留在卡上，与用户对卸载的预期不符；
4. **Android 11+**：`WRITE_EXTERNAL_STORAGE` 被系统忽略，`requestLegacyExternalStorage` 从 30 起失效——镜像在 11+ 上**静默不工作**，功能与代码意图脱节。

**修复方案**：

- **首选**：改用 `context.noBackupFilesDir` + 加密（密钥放 Android Keystore，API 23+ 用 `KeyGenParameterSpec`，19–22 退回 `KeyStore` + 固定 IV 的 AES-GCM）。代价是卸载后无法恢复，但可以通过"引导用户用手机号重新登录（一次验证码）"补偿，这是行业标准做法。
- **次选**：保留 `/sdcard/.hgtv/`，但只存**不可用于登录的**内容（设备指纹、上次观看位置），token 与 cookie 一律不进外部存储。
- 无论哪种，`WRITE_EXTERNAL_STORAGE` 都应加上 `android:maxSdkVersion="28"`。

### P0-4 播放传输层重复挂载会话拦截器

**位置**：`app/src/main/kotlin/com/hgtv/star/data/PlaybackTransport.kt:69` 与 `:78`

```kotlin
val client: OkHttpClient by lazy {
    com.hgtv.star.core.HgtvTls.configure(OkHttpClient.Builder())
        .protocols(listOf(Protocol.HTTP_1_1))
        .addInterceptor(com.hgtv.star.core.session.SessionInterceptor())   // ← 69
        ...
        // 播放取地址也走账号会话：...
        .addInterceptor(com.hgtv.star.core.session.SessionInterceptor())   // ← 78，重复
```

两行注释不同、代码相同。OkHttp 的 `addInterceptor` 不去重。

**后果**：每个播放链路响应都会：

1. 执行两次 `SessionBridge.decorate`（header 覆盖，无害但浪费）；
2. 执行两次 `sniffExpired` → 两次 `response.peekBody(32*1024).string()`——**这是把 body 复制一份到新 Buffer 再解码成 String**；
3. 执行两次 `mergeSetCookie` 与 token 轮换判定。

第 2 条发生在 `/novel/player/video_model` 的响应上，而这条接口就在**首帧关键路径**（代码自己的日志：`Stage stream +1143ms`）。对 2GB 盒子上的 32KB JSON 做两遍完整拷贝与 UTF-8 解码，是白付的。

**修复**：删掉 `:78` 那一行。

## 四、P1：架构级问题

### P1-1 God Activity：297 个可写字段，没有状态模型

**事实**：`MainActivity` 家族 15,384 行；`MainActivity.kt` 内 297 个可写字段（286 个 `internal var` + 11 个 `internal lateinit var`）。

作者用注释解释了为什么是 `internal`（`MainActivity.kt:79-87`）：

> 拆出去的那部分写成了 MainActivity 的扩展成员……**出现在别的 MainActivity* 文件里的东西不能改回 private**，否则编译不过。

这句话本身就是问题的诊断书：**拆文件只解决了"文件太长"，没解决"状态没有边界"**。任何一处代码都能改任何一个字段，编译期无法阻止。

**症状已经出现，并且被作者用补丁逐个压住**：

| 补丁 | 位置 | 它真正要解决的问题 |
| --- | --- | --- |
| `generation` | `MainActivity.kt` | 异步回调落到已失效的页面 |
| `playbackSession` | `:285` | 异步回调落到已失效的剧集 |
| `playbackWatchdogSession` | `:344` | 看门狗落到已失效的会话 |
| `failureHandledSession` + 1.5s 窗口 | `:294` | `STATE_ENDED` 与 `onPlayerError` 重复处理 |
| `danmakuToken` | `:200` | 弹幕请求串台 |
| `accountToken` | `:489` | 账号请求串台 |
| `recommendToken` / `recommendPageToken` | `:2243` | 推荐流请求串台 |

七套独立的"代际号"，各自定义、各自比较、各自重置。这是典型的**缺少单一事实来源（SSOT）**。用一个 `PlaybackSession` 数据类（含 `id`、`episodeId`、`state`、`startedAt`）配合协程的 `Job` 取消语义，可以一次性替代其中至少四套。

**建议的最小改动（不需要重写）**：

1. 把播放相关的状态（`player`、`playbackSession`、`ledger`、`preparedNext`、`queued*`、看门狗、`lastEpisodeDuration`）抽成 `PlaybackController`，放在 `app` 但**不持有任何 View**，只暴露 `StateFlow<PlaybackState>`；
2. `MainActivity` 订阅它，只做"渲染"；
3. `PlaybackController` 是纯 JVM 可测的——这直接补上 §P2-4 的 `app` 层零测试。

这一步的收益不是"代码好看"，而是：**播放链路的每个状态转换第一次变得可以写测试**。目前 279 个测试里，关于播放的只有 `PlaybackDegradationTest` / `PlaybackCacheTest` / `PlaybackAttemptLedgerTest` 三个，`playEpisode` 本体一行覆盖都没有。

### P1-2 无线程模型：22 个线程池，峰值 40+ 线程

**事实**：

| 池 | 大小 | 位置 |
| --- | --- | --- |
| `io` | 3 | `MainActivity.kt:96` |
| `playbackPrime` / `playerBuildWorker` / `networkCleanup` / `prefetchWorker` / `danmakuWorker` | 各 1 | `:106,115,174,196,198` |
| `recommendWarmWorker` | 2 | `:1051` |
| `ArtworkLoader.workers` | ≤ 8 | `data/ArtworkLoader.kt:395` |
| `ContentRepository.accountPool` | 6 | `core/ContentRepository.kt:478` |
| `SUGGEST_POOL` | 5 | `:501` |
| `homeFeed` 临时池 | 4 | `:1221` |
| `webSearch` 临时池 | N | `:1720` |
| 其余（TvTools / Library / FavoriteMonitor / 3 个写队列 / 3 个缓存写线程 / SessionKeeper / HgtvDns / DanmakuEmoji） | 各 1 | 散落 |

在 2GB 电视盒子上，线程栈按默认 1MB 计，40 条线程 ≈ 40MB 虚拟内存；实际物理占用低得多，但**调度竞争是真实的**：8 个图片解码线程 + 6 个账号请求 + 4 个榜单请求同时跑在 4 核 A53 上，播放线程拿不到稳定时间片，表现就是"一边滚列表一边播就卡"。

`homeFeed()` 与 `webSearch()` 更值得注意：**每次调用都 `newFixedThreadPool` 然后 `shutdownNow()`**（`ContentRepository.kt:1221-1235`、`:1720-1730`）。在低端设备上反复创建/销毁线程池是明确的浪费，而且 `shutdownNow()` 会中断正在跑的请求——代码靠 `runCatching` 吞掉中断异常，这正是 301 处 `runCatching` 里的一批。

**建议**：

1. 引入 `kotlinx-coroutines-android`，用**一个** `Dispatchers.IO.limitedParallelism(n)` 替代除播放专用之外的池；
2. `homeFeed` / `webSearch` 改用共享池 + `coroutineScope { async {} }`，取消走结构化并发，不再需要 `RequestScope`；
3. 保留 `playbackPrime` / `playerBuildWorker` 的独立性（作者的理由是对的：不能排在网络后面），但用 `Dispatchers.IO.limitedParallelism(2)` 的命名调度器表达。

**代价**：`RequestScope`（154 行）与 `Cancellable` 的整套机制可以删掉，约减 300 行；但需要重写约 20 个调用点。这是**净减少**代码的改动。

### P1-3 播放进度每 5 秒全量重写 200 条历史

这是我在数据层找到的最实在的性能问题，链条完整：

```
MainActivity.kt:1589   if(player?.isPlaying==true && now-lastSaved>5000) { saveProgress(); lastSaved=now }
   ↓
Library.kt:282         fun save(progress) { if (state().save(progress)) persist("progress", "historyDeleted") }
   ↓
Library.kt:247         "progress" -> state.history().let { rows -> { LibraryDisk.history(rows) } }
   ↓
LibraryIndex.kt:221    fun history(rows) = JSONArray(rows.map { p -> JSONObject().put("series", p.series.toJson())... }).toString()
   ↓
Library.kt:1590        return edit.commit()      ← 同步 fsync
```

**量化**（假设：历史 200 条满、收藏 500 条、稍后看 100 条；每条 `Series` 序列化后约 0.5KB——`Series.toJson()` 共 14 个字段，其中 `description` 在这条路径上**没有截断**）：

| 项 | 每次 | 播放 1 小时（720 次） |
| --- | --- | --- |
| 构造 `progress` JSON 字符串 | 200 × 0.5KB ≈ **100KB** | ≈ 72MB 临时字符串 |
| `commit()` 重写的整份 XML | (200+500+100) × 0.5KB ≈ **400KB** | ≈ **288MB 文件写入** + 720 次 fsync |

而这一整条链要保存的信息，本质上是 `(seriesId, episodeIndex, position, duration, updatedAt)` 五个值——**不超过 60 字节**。

对 eMMC 来说 288MB/小时是实打实的磨损；对 2GB 盒子来说，`JSONObject`/`JSONArray` 的构造与 `toString()` 都发生在写线程上，而写线程的 fsync 会阻塞 5–50ms，`LatestWriteQueue` 的 250ms 合批窗口经常装不满就落盘。

**这不仅是性能问题，也是数据安全问题**：`take(200)` 意味着看过 200 部之后，最早的记录被静默丢弃——用户会发现"历史里少了东西"，而界面没有任何提示。

**建议**：

1. **短期（半天）**：`persist` 只写当前这一条。把 `progress` 拆成 `progress:<seriesId>` 单键，`LibraryIndex` 内存里仍持有 200 条，但落盘只写变化的那一条。写放大降到 1/200。
2. **中期（2–3 天）**：迁到 Room。一张 `watch_progress` 表，`UPSERT` 一条记录，写放大 O(1)，且能做 `ORDER BY updated_at DESC LIMIT 200` 的分页查询，不必每次全量排序。
3. **同时**：把保存间隔从 5s 放宽到 15–30s，并在 `onPause` / 换集 / 退出时强制落盘。用户能感知的"续播精度"是 15 秒级，5 秒纯属浪费。

### P1-4 播放器栈停在 EOL 版本，且未用电视关键能力

**现状**：`exoplayer-core:2.19.1` + `exoplayer-ui:2.19.1`（2023-01）。Google 自 2022 年起全线转向 **Media3**，ExoPlayer 2.x 已停止接收安全与兼容性修复。

**未启用的电视侧能力**：

| 能力 | 现状 | 影响 |
| --- | --- | --- |
| **Tunneling**（`setTunnelingEnabled`） | 未使用 | 4K/HDR 通路无法走硬件直通，CPU 占用与音画不同步风险都更高。这是 Android TV 上收益最明确的一项 |
| **异步 MediaCodec**（`AsynchronousMediaCodecAdapter`） | 未启用（但 baseline profile 里列了该类，说明库里带着） | 解码线程阻塞减少，首帧与 seek 更快 |
| **字幕轨**（`TrackSelectionParameters` / `TextRenderer`） | **完全没有**（全仓 0 处 `TextTrack` / `SubtitleView` 业务代码） | 短剧基本不需要，但"音视频应用"缺字幕是能力缺口 |
| **音轨选择** | 无 | 无国语/粤语、无解说轨切换 |
| **`SurfaceView` 渲染路径** | 只有 `SurfaceTexture`（`player_surface_texture.xml`） | 部分盒子在 HDR / 高帧率下 SurfaceTexture 路径性能差于 SurfaceView |

**自定义数据源的对象分配**：`player/VideoDataSource.kt:54`

```kotlin
buffer = video.read(position, minOf(want, remaining).toInt())   // 每次返回新 ByteArray，最大 2MB
```

`RemoteVideo.read()` 每次都新建数组（`RemoteVideo.kt` 的 `range()` → `body.source().readByteArray(n)`），`VideoDataSource` 再 `copyInto` 到 ExoPlayer 提供的 buffer。也就是说每个 2MB 分片产生**一次 2MB 分配 + 一次 2MB 拷贝**。播放 1 小时按 1.6Mbps 算约 720MB 流量 → **约 720MB 的临时分配**，全部落在播放线程上。

对 2GB 盒子（`maxMemory` 通常 192–256MB）来说，这是 GC 压力的主要来源之一。作者已经在 `PlaybackCache` 里注意到"预分配到底"（`MediaCrypto.kt` 的 `ArrayList<Sample>(16384)`），但这条热路径没做同样的事。

**建议**：

1. 短期：`VideoDataSource` 复用一块固定的 2MB `ByteArray`，`RemoteVideo.read` 改成"读进调用方提供的 buffer"（签名 `read(pos, len, out): Int`），消掉一半分配；
2. 中期：评估 Media3 迁移。**注意**：作者在 `PlaybackTransport.kt` 里记录了 OkHttp h2 读线程崩溃的现场，Media3 的 `DefaultHttpDataSource` 不走 OkHttp，这条历史包袱会自然消失——这是迁移的一个隐藏收益；
3. 迁移时顺带打开 `setTunnelingEnabled(true)`（需按设备能力降级）。

### P1-5 进程死亡即失忆

**事实**：全仓 `onSaveInstanceState` / `onRestoreInstanceState` **0 处**。

`restoreStoppedPage`（`MainActivity.kt:328`）只在 `onStop` 置位、`onResume` 消费，是**进程内**的。电视盒子（尤其 1–2GB 的）在后台停留几分钟就会被 LMK 回收，用户按 Home 再回来：

- 播放位置丢失（`startPosition` 是字段）
- 导航栈丢失（`screen` / `tab` / `collection` 是字段）
- 滚动位置丢失（`scrollPositions` 是 Map）
- 详情页丢失（`detail` 是字段）

表现是"回到首页"。对一个以"续播"为核心体验的短剧应用，这是明显的体验断点。

**建议**：`onSaveInstanceState` 里存一个极小的 `Bundle`（`screen`、`seriesId`、`episodeIndex`、`position`、`tab`），`onCreate` 里优先恢复。约 40 行代码，收益直接。

### P1-6 无 WAKE_LOCK、无 WifiLock

**事实**：Manifest 只声明 `INTERNET` / `ACCESS_NETWORK_STATE` / `ACCESS_WIFI_STATE` / `WRITE_EXTERNAL_STORAGE`。无 `WAKE_LOCK`。

- `syncKeepScreenOn()` 只保证**屏幕**不灭（`FLAG_KEEP_SCREEN_ON`），不保证 **CPU** 不休眠；
- 未调用 `ExoPlayer.setWakeMode(C.WAKE_MODE_NETWORK)`；
- 未持有 `WifiManager.WifiLock`。

**后果**：

1. 用户暂停后离开（比如去接电话），盒子进入 Doze，回来时连接已断，需要重走 DNS + TLS + 取地址；
2. Wi-Fi 省电模式（PS-Poll）在高码率下会造成周期性 RTT 抖动，典型症状是"播一会儿卡一下"——这是 TV 盒子最常见的报障之一，而 `WifiLock(WIFI_MODE_FULL_HIGH_PERF)` 正是它的标准解法。

**建议**：加 `WAKE_LOCK` 权限，播放中 `setWakeMode(C.WAKE_MODE_NETWORK)`，并在 `screen=="player" && isPlaying` 期间持有 `WIFI_MODE_FULL_HIGH_PERF`（`onPause` 释放）。约 30 行。

### P1-7 OkHttp 3.12.13

2018–2019 年的分支，官方已停止维护。项目自己的注释记录了它带来的线上崩溃（`PlaybackTransport.kt:17-32`）：

```
IndexOutOfBoundsException: off=0, len=1482 out of bounds (size=0)
  at ConscryptEngineSocket$SSLInputStream.processDataFromSocket
  at Http2Reader.nextFrame
```

作者的处置是**全局禁用 HTTP/2**（`.protocols(listOf(Protocol.HTTP_1_1))`）——这在视频分片场景是正确取舍（单流 Range 请求没有多路复用收益），但同时也放弃了对内容接口的复用收益，并且这是"绕过"而不是"修复"。

**建议**：升到 OkHttp 4.12（Kotlin 实现，API 兼容，`minSdk 19` 可用）。收益：h2 读线程崩溃的真正修复、TLS 1.3 改进、`EventListener` 可观测性。代价：约 1 天的回归。**不建议**为 `core` 模块的 `org.json` 冲突做特殊处理——现在用 `exclude(group="org.json")` 绕开，升 4.x 后可去掉。

## 五、P2：体验与工程化

### P2-1 固定 1280×720 画布在手机上偏小

> **勘误（重构时发现）**：本节初稿用了竖屏尺寸 1080×2400 计算，而 Activity 声明的是
> `screenOrientation="landscape"`，实际拿到的是 2400×1080，缩放是 `min(2400/1280, 1080/720)=1.5`
> 而不是 0.84。因此下面的「三分之一」结论过于悲观，真实情况是「约 9.6sp，明显偏小」。
> 结论方向不变（手机端字确实偏小），量级已修正。

`tv/TvMetrics.kt` 的设计：`designScale = min(w/1280, h/720)`，所有尺寸乘以它。

在 2400×1080 的手机横屏上，`designScale = min(1.875, 1.5) = 1.5`。设计稿 16px 正文 →
**24 物理像素**；而同一台机器上系统标准的 16sp 正文是 `16 × 400/160 = 40` 物理像素。
也就是说手机上的字只有系统标准的 **60%**（约 9.6sp），明显小于正文。

作者在 `TvMetrics.kt` 的注释里说明了为什么不用 dp（"density 是厂商随手填的数"）——这个理由在**电视上成立**，因为电视的物理尺寸与观看距离把这个问题掩盖了；但在**手机上不成立**，手机的 density 是准确的。

README 声称"手机 / 平板 / 电视"三端支持，实际手机端可读性不足。

**建议**：`designScale` 按 `DeviceForm` 分档——`TV` 用现有逻辑，`PHONE` / `TABLET` 用 `min(w/960f, h/540f)` 或直接引入一个 `phoneScale = 1.6f` 的乘子。这是纯数值改动，不影响布局结构。

### P2-2 无全局过扫描安全区

横向：`pageInset = dp(78)`，`78/1280 = 6.1%`，对绝大多数电视的 5% 过扫描是够的。

纵向：**没有对应的余量**。页面内容从 `y = 0` 开始，首行内边距只有 `dp(24)`–`dp(28)`（`MainActivityDetail.kt:215,605` 等），占 720 设计高度的 **3.3–3.9%**——小于常见的 5% 过扫描裁切量，也小于那条 `TOOLBAR_HEIGHT = 88` 的工具条本身的高度。也就是说在过扫描 5% 的电视上，工具条顶部与首行海报的上沿会被切掉。

而 `DanmakuView.kt:77` 单独为弹幕写了 `TOP_MODE_INSET_DP = 20` 并注明"躲开电视过扫描"——说明作者知道这个问题存在，只是没有把它提升为全局策略。

**建议**：在 `root` 上加一层 2.5% 的安全内边距（或提供设置项"屏幕边距：无 / 小 / 大"）。电视端这是标配。

### P2-3 无障碍支持薄弱

电视端的 TalkBack（Android TV 的语音辅助）依赖 `contentDescription`；手机端的读屏同样。当前状态下，一个纯图标按钮（返回、搜索、设置）在读屏里是"按钮"，没有名字。

**建议**：在 `TvButton` 工厂（`MainActivityLayout.kt:158`）里统一注入 `contentDescription = label`，图标按钮强制传 `label`。一处改动覆盖全站。

### P2-4 app 层零测试

### P2-5 无崩溃可观测性

移除友盟（统计 + APM）是**正确的决定**（`proguard-rules.pro` 里有完整说明，APK 从 4.2MB 降到 2.4MB）。但移除之后没有替代方案：

- 无 `Thread.setDefaultUncaughtExceptionHandler`
- 无本地崩溃落盘
- 无 opt-in 上报

`Diagnostics` 只覆盖**被 `runCatching` 捕获的**异常（301 处）。未捕获的异常直接让进程消失，用户只能报"闪退了"，开发侧零信息。

这与项目在其他方面的细致程度（`DebugOverlay` 834 行、`PlaybackDiagnostics` 1007 行）形成反差：**能观测的都被观测了，唯独最致命的那个没有**。

**建议**：加一个 `UncaughtExceptionHandler`，把堆栈 + 设备信息 + 最近 50 行 `DebugLog` 写到 `filesDir/crash/`，设置页提供"导出崩溃日志"。零隐私风险、零第三方依赖，约 80 行。

### P2-7 `ArtworkCache.put` 在全局锁内做文件写入

`data/ArtworkCache.kt:95-109`

```kotlin
@Synchronized fun put(key: String, bytes: ByteArray) {
    ...
    temp.writeBytes(bytes)          // ← 文件 IO 在锁内
    if (!temp.renameTo(dest)) { ... }
```

注释里已经分析了锁竞争（"`put` 是 `@Synchronized`，8 个 worker 全排在它后面"），并为此把 `prune` 从"每次写"改成"涨过上限才扫"。但**根本问题没动**：磁盘写入本身仍在监视器内。

**建议**：锁只保护内存计数（`knownBytes` / `knownCount`），`writeBytes` + `renameTo` 移到锁外。用 `ConcurrentHashMap<String, Long>` 维护大小索引即可。

### P2-8 DNS 12 小时旧 IP 兜底

`core/HgtvDns.kt:46-48, 122-127`：系统解析失败时，退回盘上 **12 小时**内的旧 IP（视频 CDN 域名除外）。

这个设计有明确的现场依据（"TCL 电视上某域名系统解析恒为 EAI_NODATA"），取舍也写得很清楚。但风险在于：NAT 表项或负载均衡变更后，旧 IP 可能"能建连但一直超时"，而此时系统 DNS 是好的——用户看到的是"某些剧永远打不开"，且**杀进程重进也一样**（盘上那份还在）。

代码已经为视频域名开了豁免（`isVideoHost`），说明作者意识到了。建议把豁免扩大到"任何需要建连的域名"，或者把兜底 TTL 从 12 小时压到 30 分钟——DNS 缓存的价值在冷启动那 1.6 秒，30 分钟足够覆盖一次会话。

## 七、明确不建议做的改动

专家评审的价值一半在于说"不要做什么"。

| 不建议 | 理由 |
| --- | --- |
| **为了 `targetSdk 34+` 直接跳版本** | `requestLegacyExternalStorage` 一失效，`/sdcard/.hgtv/` 的镜像恢复立刻断掉。必须先落地 P0-3 的替代方案，再动 targetSdk。这两件事的顺序不能反 |
| **迁移到 Jetpack Compose** | 现有资产是 20 套主题 + 手写新拟态 + 一套经过大量现场调试的电视焦点链（"全站焦点原则"那段注释记录了至少 5 类真实 bug）。Compose 的 TV 焦点模型与 `Leanback` 差异大，迁移成本远超收益 |
| **把 `lowEndTv()` 换成 `isLowRamDevice()`** | 作者在 `compat/Platform.kt` 里已经踩过：`ro.config.low_ram` 在 2GB 电视盒子上几乎恒为 false，只看它会让整个应用按高端机跑。这个判断是对的，不要"简化" |
| **加第三方统计 / APM 来"解决可观测性"** | 移除友盟让 APK 从 4.2MB 降到 2.4MB，是正确的取舍。可观测性的缺口应该用本地崩溃落盘 + opt-in 上报补，不是把 SDK 加回来 |
| **把 `runCatching` 全部改成显式 try/catch** | 301 处不可能一次改完，且多数场合"降级为没有结果"是合理的产品行为。应该改的是**让失败可区分**（`Result<T>` 或 sealed `Outcome`），从新增代码开始，逐步替换 |
| **给 `PlaybackTransport` 打开 HTTP/2** | 作者记录的 h2 读线程崩溃是真实线上事故，禁用 h2 是正确的规避。真要恢复，前提是先升 OkHttp 4.x |
| **把 `AesV3` / `MediaCrypto` 换成标准 AES** | 这是协议层的自定义变换（注释写明"Protocol-specific transform, not standard AES"），换掉就连不上服务端。它们不是"加密实现得不好"，是"必须这样" |

## 八、值得保留的设计

评审报告如果只列问题，会让人误以为这个项目一团糟。以下这些做法在同类项目里很少见，建议在新架构里**原样保留**：

1. **基线 profile 的落地链路**（`app/build.gradle.kts:71-78`）：`baseline-prof.txt` + `profileinstaller`，注释里给了实测对比（`Displayed +3s380` vs `+837ms`）。多数团队根本不知道 `speed-profile` 遇到空 profile 什么都不编。
2. **首块 512KB 策略**（`VideoDataSource.kt:52-54`）：首帧只要一个 I 帧，2MB 是浪费。这是"读懂了自己链路"才会做的优化。
3. **播放索引落盘 + 异步写**（`PlaybackCache.kt:84-88`）：把 139ms 的写盘从首帧路径挪走，且只缓存"下一次起播用得上"的东西。
4. **R8 剥日志 + `-keepnames Throwable`**（`proguard-rules.pro`）：既省了 UI 线程上的字符串拼接，又保证现场异常类名可读。这两条同时做到的不多。
5. **弹幕的"排版一次、绘制零测量"**（`DanmakuView.kt`）：`measureText` 全部前置到 `relayout`，每帧只做算术。配合"同速不追尾"的轨道算法，低端 GPU 上 160 条/帧仍有余量。
6. **`LatestWriteQueue` 的失败重试语义**（`core/LatestWriteQueue.kt:39-48`）：失败时保留旧快照但让新值优先，两次退避重试。这是认真想过"落盘失败之后怎么办"的代码。
7. **279 个单元测试 + 固定向量**：`core` 模块能做到这个覆盖率，说明分层是对的——**问题不在分层，在于 `app` 层没有跟着分**。
