## 二、依赖换代：两条硬约束

### 2.1 Media3 被 minSdk 19 钉在 1.4.1

```
androidx.media3:media3-exoplayer  2.19.1 (ExoPlayer 2)  →  1.4.1
```

ExoPlayer 2.x 已停止维护，官方全线转向 Media3。但 **Media3 从 1.5.0 起要求 `minSdk 21`**：

| 版本 | minSdk |
| --- | --- |
| 1.3.1 | 19 |
| 1.4.1 | **19（最后一版）** |
| 1.5.1 | 21 |
| 1.6.1 | 21 |

Android 4.4 是本应用的主力机型，因此只能停在 **1.4.1**。这不是「懒得升」，是版本边界。
将来若要继续升 Media3，必须先把 `minSdk` 抬到 21——那是一次产品决策，不是技术决策。

### 2.2 OkHttp 3.12.13 → 4.12.0

3.12.13 是 2018–2019 年的分支，官方早已停止维护；项目自己记录的线上崩溃
（`ConscryptEngineSocket` 里 `IndexOutOfBoundsException`，见 `PlaybackTransport` 的类注释）
正是 3.x 的 h2 读线程问题。

4.x 是 Kotlin 实现，把 3.x 的 getter（`body()` / `code()` / `url()` …）改成了属性，
且标了 `DeprecationLevel.ERROR`——因此这不是「建议改」，而是**编译错误**，必须逐点迁移。
迁移是机械的：getter → 属性，`MediaType.parse(x)` → `x.toMediaType()`，
`RequestBody.create(t, b)` → `b.toRequestBody(t)`。

**注意**：`okhttp3.Call.request()` 与 `Interceptor.Chain.request()` 在 4.x 里**仍是方法**
（Kotlin 接口里声明为 `fun request()`），只有 `Response.request` 是属性。这条差异很容易被
「统一改成属性」的脚本误伤。

### 2.3 协程

新增 `kotlinx-coroutines-android:1.8.1` / `kotlinx-coroutines-core:1.8.1`，
API 19 可用，无原生库。

### 2.4 迁移时漏掉的两处（真机崩溃的直接原因）

包名迁移只扫了 `kotlin/` 下的 `.kt`，漏了两类**非 Kotlin** 的引用。第一处导致真机崩溃，
第二处导致冷启动优化静默失效。

#### （1）布局 XML 里的类名 → 崩溃

`res/layout/player_surface_texture.xml` 第 18 行还写着
`<com.google.android.exoplayer2.ui.PlayerView ...>`。这个类在依赖换代后已经不存在，
运行时抛：

```
android.view.InflateException: Binary XML file line #18:
  Error inflating class com.google.android.exoplayer2.ui.PlayerView
Caused by: java.lang.ClassNotFoundException:
  Didn't find class "com.google.android.exoplayer2.ui.PlayerView"
    at MainActivityPlayerKt.playEpisode(MainActivityPlayer.kt:720)
```

**为什么编译期发现不了**：XML 里的类名是字符串，`LayoutInflater` 到运行时才 `Class.forName`。
编译、安装、首页、普通播放全部正常，**只有打开「竖屏短剧全屏」且设备形态被判定为
手机 / 平板时**才会 inflate 这份布局——于是它成了一个只在特定开关下触发的崩溃。

已改成 `androidx.media3.ui.PlayerView`（`app:surface_type="texture_view"` 等属性名在
Media3 里保持不变）。

> 教训：换播放内核时，`res/` 与 `AndroidManifest` 里的类名要一起搜。
> `grep -rn "com.google.android.exoplayer2" android/app/src/main/res` 一条命令就能发现。

#### （2）`baseline-prof.txt` 里的 62 个类 → 优化失效

ART 的 AOT 清单里，`com/google/android/exoplayer2/**` 共 62 行。迁移之后这些类一个都不存在，
系统会**静默跳过**无效条目——不报错、不警告，只是「冷启动按 profile 预编译」这件事对
播放链路完全失效，而播放链路正是冷启动最重的那一段。

已按包名映射到 `androidx/media3/**`，并**逐个到 Media3 的 jar 里核对类是否真的存在**：
56 条迁移成功，6 条在 Media3 中已不存在（`SimpleExoPlayer`、`RendererHolder`、
`FlacExtractor`、`Mp4Box`、`TextRenderer`、`EventDispatcher`）直接剔除。
现在文件 551 行、`exoplayer2` 出现 0 次。

> 这是人工映射，不是生成结果。后续应接 `BaselineProfileRule` 在真机上自动生成，
> 见 §13 第 3 条。

#### （3）正则改写丢了括号 → 二维码登录打空主机

OkHttp 3 → 4 的迁移脚本用一条正则把 `HttpUrl.parse(X)` 改写成 `X.toHttpUrlOrNull()`。
`QrLogin` 里那一行原本是：

```kotlin
val url = HttpUrl.parse(HOST+path)?.newBuilder()      // 先拼成绝对地址，再解析
```

脚本的捕获组是 `([^()]+)`（不跨括号），于是 `HOST+path` 被整体捕获、**括号被丢掉**：

```kotlin
val url = HOST+path.toHttpUrlOrNull()?.newBuilder()   // 只解析 path，再和 HOST 拼
```

`path` 是相对路径（`/passport/web/get_qrcode/`），`toHttpUrlOrNull()` 返回 null，
`HOST + null` 拼出 **`https://api5-normal-lq.fqnovel.comnull`**。
编译通过、类型正确、`core:test` 全绿——只有真机点「扫码登录」才会打到一个不存在的主机，
用户看到的是「无法显示二维码」。

已修：`(HOST + path)` 先拼再解析，并抽成 `QrLogin.endpoint(path, params)`，
配 4 个单测（`QrLoginUrlTest`）把主机名、路径、查询参数逐个钉死。

> 教训：**机械改写要检查运算优先级与括号**。`f(a+b)` → `a+b.g()` 这类改写，
> 语法合法、类型正确、编译通过，是最难在评审里发现的一种错。
> 凡是改写后改变了「谁先算」的地方，都要么保留括号，要么像这里一样抽成可测函数。

## 三、线程模型

### 3.1 改造前

| 归属 | 池 | 线程数 |
| --- | --- | --- |
| `MainActivity` | `io` / `playbackPrime` / `playerBuildWorker` / `networkCleanup` / `prefetchWorker` / `danmakuWorker` / `recommendWarmWorker` | 3+1+1+1+1+1+2 |
| `ContentRepository` | `accountPool` / `SUGGEST_POOL` / 首页四栏（每次新建） / 官网搜索（每次新建） | 6+5+4+N |
| 其它 | 图片 / 弹幕表情 / 写盘 / 心跳 / DNS / 会话 | 若干 |

峰值 **40 条以上**，且前两组**属于 Activity 实例**：每次重建新建一批、`onDestroy` 再
`shutdownNow()`。这既让线程数随重建抖动，也制造了「任务提交到已关闭的池」这类崩溃面。

### 3.2 改造后

线程预算收在 `core/WorkLanes.kt`（纯 JVM，界面与网络层共用同一份），按用途分道：

| 道 | 线程 | 干什么 | 依据 |
| --- | --- | --- | --- |
| `network` | 4 | 内容接口、账号、推荐流、预取、播放地址 | 冷启动同时有「首页 + 推荐 + 账号 + 预取」在跑，再多只是把带宽切碎 |
| `fanout` | 6 | 扇出型并发（首页四栏、热搜种子、账号七请求、官网搜索十页） | 这些任务**由同一个调用方 join**，必须容纳最大扇出，否则并发退化成串行 |
| `player` | 2 | 建播放器、枚举解码器、预热下一集 | 建播放器实测 0.5 秒（`MediaCodecList` 全表扫描），不能排在网络后面 |
| `danmaku` | 1 | 弹幕分页拉取 | 一集要按 30 秒窗口连拉几十页 |
| `disk` | 1 | 本地记录与缓存落盘 | 串行落盘天然正确，且不和播放读盘抢 IO |

每条道同时暴露 `executor`（给既有 `submit` / `Future`）与 `dispatcher`（给协程），
**跑在同一批线程上**，因此预算只有一份。

### 3.3 页面级协程作用域

`MainActivity.appScope = CoroutineScope(SupervisorJob() + Dispatchers.Main)`，
`onDestroy` 里 `appScope.cancel()`。

分工很明确：

* **线程池是进程级资源**（不随页面销毁）；
* **作用域是页面级生命周期**（随页面销毁取消）。

改造前两者混在一起（池属于 Activity），才有了那七个 `shutdownNow()`。现在
`onDestroy` 只取消协程，**不碰线程池**——否则重建后的新 Activity 会往已关闭的池里提交任务。

调用点用 `appScope.network { }` / `appScope.player { }` 这样的命名扩展（`architecture/Lanes.kt`），
一眼能看出这段活儿跑在哪条道上。

### 3.4 为什么不是「全部改成协程」

既有的网络调用是 OkHttp 的**同步** `execute()`，取消语义是**线程中断**
（`core/RequestScope` 的整套机制就是为此存在的）。`Job.cancel()` 不会中断阻塞中的线程，
贸然替换会让「切页 / 换剧时取消在途请求」失效——那是比线程数更重要的事。

因此边界划在这里：

* **需要取消语义的**（`prefetchJob` / `workJob` / `relatedJob` / `suggestJob` /
  `buildPlayerAsync`）继续用 `Future` + `RequestScope`；
* **fire-and-forget 的**（预连接、类预热、弹幕拉取、传输清理）改成协程，随页面销毁取消。

这个取舍写进了 `WorkLanes` 与 `Lanes` 的注释，避免下一个人「统一一下」把取消语义弄丢。

## 四、状态模型

### 4.1 问题

改造前「第几次播放、播到哪一步」由七个计数器分担：

| 计数器 | 要挡的问题 |
| --- | --- |
| `playbackSession` | 异步回调落到已失效的剧集 |
| `generation` | 异步回调落到已失效的页面 |
| `failureHandledSession` | `STATE_ENDED` 与 `onPlayerError` 重复处理 |
| `playbackWatchdogSession` | 看门狗落到已失效的会话 |
| `danmakuToken` | 弹幕请求串台 |
| `accountToken` | 账号请求串台 |
| `recommendToken` | 推荐流请求串台 |

七套各自定义、各自比较、各自重置。这是缺少单一事实来源的典型症状。

### 4.2 结构

```
core/playback/PlaybackState.kt     PlaybackPhase / PlaybackState / PlaybackFailure
core/playback/PlaybackMachine.kt   reduce(状态, 事件) = 新状态（纯函数）
app/architecture/PlaybackController.kt   持有 StateFlow、会话号、事件入口
```

**五条迁移规则**（写在 `PlaybackMachine` 的 KDoc 里，并有对应单测）：

1. 旧会话的事件一律丢弃（`Open` 除外——它本身就是建立新会话）；
2. `prepared` 只进不退：一旦 READY 过，后续 BUFFERING / ENDED / FAILED 不再把它清回 false；
3. `FAILED` 只能由非 IDLE 状态进入，且必须带 `PlaybackFailure`；
4. `ENDED → READY` 合法（用户往回拖）；
5. 进度钳制在 `[0, duration]`，`duration == 0` 时不钳上界（直播 / 时长未解析）。

### 4.3 兼容层

`playbackReady` 与 `playError` 这两个用了 31 次的字段**没有删除**，而是改成控制器状态的
只读投影：

```kotlin
internal var playbackReady: Boolean
    get() = playback.prepared
    set(value) { playback.setPrepared(value) }

internal var playError: Boolean
    get() = playback.failed
    set(value) { playback.setErrorFlag(value) }
```

理由：那 5 处赋值分散在三个文件、每处都夹在一长串副作用中间。逐个改写成
`onPlayerState(...)` 会让这次重构的 diff 无法审阅，而收益是零——语义已经唯一了。

`playbackSession` 同理：改成 `playback.sessionId` 的只读投影，原来两处 `++`
（`playEpisode` 与 `detachPlayerSurface`）合并成 `PlaybackController.beginSession()`。

**这里踩过一个坑**：`beginSession()` 最初只递增计数器、没有把新号写回状态，
于是 `playbackSession` 读到的还是旧值——「作废旧回调」当场失效。修法是
`_state.update { it.copy(sessionId = id) }`：只作废回调，不改阶段与 `prepared`。

## 五、数据层

### 5.1 播放进度：一剧一文件

改造前的链路：

```
tick 每 5 秒 → saveProgress() → Library.save()
  → persist("progress") → 200 条历史全量序列化成 JSON（约 100KB）
  → SharedPreferences.commit() → 整份 XML（约 400KB）重写 + fsync
```

按播放一小时 720 次算，约 **288MB 文件写入 + 720 次 fsync**，而真正变化的只有
「这一部播到第几秒」——不到 60 字节。

现在：`data/ProgressStore.kt`，一剧一个 `filesDir/library/progress/<seriesId>.json`（约 0.5KB），
写盘走 `disk` 车道，`tmp + rename` 保证原子性。**写放大从 O(200) 降到 O(1)**。

配套改动：

* 落盘间隔 5 秒 → **15 秒**（`PROGRESS_SAVE_INTERVAL_MS`）。换集 / 暂停 / 退出 /
  退到后台都会额外强制落盘，正常使用几乎不会真的丢进度。
* 墓碑（`historyDeleted`）只在「这部剧之前被删过」时才重写，不再每次保存都带上。
* 一次性迁移：目录为空且旧 `progress` 键有内容时，拆成文件后删掉旧键。
  迁移前先 `count()`，避免每次启动都去解一遍 100KB 的旧 JSON。
* 删记录 / 清空记录会同时删文件（否则内存里删了、盘上还在，下次启动又读回来）。

### 5.2 图片缓存锁

`ArtworkCache.put` 原本整个方法是 `@Synchronized`，`writeBytes` 也在锁内——8 个图片线程
全排在这一次磁盘写后面。现在锁只保护两个计数，写盘与 `rename` 在锁外；`prune` 自己加锁。

### 5.3 DNS 兜底

`FALLBACK_TTL_MS` 从 12 小时压到 **30 分钟**。12 小时的旧 IP 在 NAT / 负载均衡变更后
会「能建连但一直超时」，且杀进程重进也一样（盘上那份还在）。这份缓存的价值是冷启动那
1.6 秒，30 分钟足够覆盖一次观看会话。

## 六、播放器能力：评估结论

`P1-4` 列了五项。逐项结论如下——**没有全部采用，理由写在代码注释里**。

| 能力 | 结论 | 理由 |
| --- | --- | --- |
| Media3 换代 | ✅ 采用 | 见 §2.1，钉在 1.4.1 |
| `setWakeMode` + `WifiLock` | ✅ 采用 | 见 §7，解决「暂停一会儿回来放不了」「播一会儿卡一下」 |
| **Tunneling** | ❌ 不采用 | 隧道模式要求 `SurfaceView`，而本应用的「竖屏短剧全屏 / 画面缩放」依赖 `TextureView` 的父级变换（`MainActivityPlayer.kt` 有完整说明：SurfaceView 是独立图层，父视图旋转不作用到它，转完就是横向拉伸）。为 1080P 短剧换掉这两个功能，收益不成立 |
| **异步 MediaCodec** | ❌ 不采用 | Media3 1.4.1 的默认仍是同步。异步模式在廉价盒子上历史故障率更高（黑屏 / 首帧不出），而本应用的机型分布正是廉价盒子。稳定性优先 |
| **字幕轨** | ❌ 不采用 | 平台不下发字幕轨（短剧本身没有），加一套永远没有内容的 UI 是死代码 |
| **音轨选择** | ⏸ 未做 | 平台只下发单音轨，没有可选对象。留待将来真有双音轨内容时再补 |

这一节是这次重构里唯一「明确不做」的部分。不做不是遗漏，是权衡——把理由写在这里，
比默默加一个会破坏「竖屏全屏」的开关要好。

## 七、电源与网络保活

`architecture/PlaybackPower.kt`：

* `ExoPlayer.setWakeMode(C.WAKE_MODE_NETWORK)`：播放期间持 `PARTIAL_WAKE_LOCK`。
  必须在应用线程调（`ExoPlayerImpl` 第一句就是 `verifyApplicationThread()`），
  因此放在 `configurePlayer` 而不是 `buildPlayer`（后者跑在 io 线程）。
* `WifiLock(WIFI_MODE_FULL_HIGH_PERF)`：解决 Wi-Fi 省电模式造成的周期性卡顿。

两者由 `syncKeepScreenOn()` **同一个**状态同步点驱动——它本来就已经按
「前台 + 播放页 + 没出错 + 未定时停止 + 正在播」算过一次布尔量。分散在两处各写一次，
迟早会漏掉一条新路径。

Manifest 补 `WAKE_LOCK` 权限。

## 八、进程死亡后的恢复

新增 `onSaveInstanceState` / `restoreLastScreen`，只存六个值：

```
screen / tab / collection / seriesId / episodeIndex / position
```

**不存整页状态**：`Bundle` 走 Binder，上限 1MB，塞一个剧集列表进去就是
`TransactionTooLargeException`。剧集对象本身不用存——它已经在本机历史里，
按 `seriesId` 反查即可。

恢复策略：

* 播放页 / 详情页 / 推荐页 → `openDetail(series, resume = true, autoplay = false)`，
  回到那一集、**不自动出声**（用户可能是按 Home 离开的）；
* 其它页面 → 回到原来的标签 / 集合页。

## 九、界面适配

### 9.1 设计画布按形态分档 —— **已整体回退**

曾经做过：电视用 1280×720、手机 / 平板用 960×540，让手机上的版面整体放大 1.33 倍
（理由是手机横屏 2400×1080 上 16 设计 px 只有约 9.6sp，比系统正文小）。

**真机装上去之后用户的第一反馈是「整块界面明显变大」，要求恢复原版尺寸。已全部撤销。**

为什么当时的推理对、结论错：换画布不是「把字放大」，而是**把整套版式等比放大**——
按钮高度、卡片尺寸、行间距、圆角、一屏能放几行，全都跟着变。用户要的是「原来的版面，
字可能小一点」，不是「所有东西都变大一号」。

现在 `designScale()` 恢复成改造前的实现，所有形态共用 1280×720，
`TvMetrics.kt` 的代码与 `v1.2.8` 完全一致（只剩注释差异）。

> 如果将来确实要调手机上的可读性，正确做法是**只放大字号**——
> 在 `TextView.designTextSize` 里加一个形态系数，版面几何一个像素都不动。
> 这条写进了 `designScale()` 的注释，避免下一个人再动画布。

### 9.2 过扫描安全区 —— **已回退**

曾经做过：电视的 `base()` 纵向留白从 `dp(12)` 加到 `dp(36)`（约 5%），
用来覆盖电视 3~5% 的过扫描裁切。

**同样撤销了**：它不改尺寸，但会改变电视上原有的版面留白（一屏行数、首行位置都跟着动），
而它只是 P2 级的观感优化，不值得拿已经调好的版式去换。

真要支持，应该做成**设置项（默认关闭）**——让遇到切边的用户自己开，
而不是给所有人默认加边距。

### 9.3 无障碍

`button()` 是全站唯一的按钮工厂，在这里统一注入 `contentDescription = label`。
纯图标按钮（返回 / 搜索 / 设置）在读屏里终于有名字了。

**这一项保留**：它不改任何几何，对视觉零影响，只在读屏软件里生效。

## 十二、真机回归清单

改动触及播放链路，建议按这个顺序过一遍：

1. **冷启动** → 推荐页自动起播，首帧时间与 1.2.8 对比（不应变慢）；
2. **切集** → 无感切集不黑屏；选集面板换集正常；
3. **暂停 3 分钟再回来** → 能接着播（`WAKE_LOCK` 生效）；Wi-Fi 下播 10 分钟无周期性卡顿；
4. **按 Home 杀进程** → 重新打开应回到原来那一集（`onSaveInstanceState`），且不自动出声；
5. **看 3 部剧后退出** → 历史正确；`filesDir/library/progress/` 下应有 3 个 json；
6. **删除某条历史** → 对应 json 消失，重启后不再出现；
7. **升级安装**（覆盖 1.2.8）→ 旧历史完整迁移到文件，`shared_prefs` 里 `progress` 键消失；
8. **竖屏短剧全屏**（手机）→ 画面真的转 90°，不是拉伸；
9. **界面尺寸** → 与 1.2.8 逐像素一致（画布、留白、字号均未改）；只应看到图标按钮在
   读屏里有了名字，视觉上无差别。
