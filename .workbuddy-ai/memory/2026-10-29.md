## 播放失败重试 / 降级逻辑审核（只审不改）

审了 `core/PlaybackDegradation.kt`、`MainActivityPlayback.kt`（playerFailure / replayWithPlan /
recoverQueuedCurrent / resetBudgetsForManualRetry）、`PlaybackDiagnostics.kt`（两条看门狗 /
recoverFormalPicture）、`MainActivityPlayer.kt`（playEpisode / applyDecoderMode）、
`core/Watching.kt`（RecoveryBudget）、`data/PlaybackCapability.kt`。

确认的主要缺口（按优先级）：

1. 音频故障没有恢复路径：`decide()` 对 AUDIO 直接 null，`limitOf(AUDIO)=0`；
   且错误页两颗按钮（切换为软解 / 换到 xP）只看 `playbackDecoderMode`，不看媒体类型 → 对音频无效。
2. 队列项（下一集）的连接类故障在「未到片尾」时被归因到**当前集**：
   `failingEpisode` 用 `queuedNearEnd` 判定，会 forgetStream 当前集、重放当前集。
3. 播到一半进入 BUFFERING 无限转圈没有任何看门狗覆盖（起播看门狗首帧后已撤，
   停帧看门狗要求 STATE_READY）。
4. 起播看门狗 `playbackWatchdogAt` 在用户暂停时不重置 → 暂停 >90s 后恢复播放立即误判 stall_buffer。
5. 看门狗 tick(15s) == 阈值(15s)，最坏 30s 才动手。
6. 错误页 → 返回前台走 `playEpisode(recovering=false)` → 预算全量归还，「每集有界」不成立。
7. 手动重试三份额度口径不一致：`requestPlayback` 只还 session 那一份；
   `onManualRetry()` 拒绝归还时 `resetBudgetsForManualRetry` 仍重置其余三份。
8. 5xxx（AudioTrack 初始化 / 写入失败）既不重试也不降级，直接死路。

结构性问题：六套预算（SessionPlaybackPolicy / RecoveryBudget / formalPictureRecoveries /
queuedRecoveries / streamRetriedFor / autoNextFailures）分散三处、五种重置条件，
`decide()` 用可变字段 `manualHint` 当「为什么放弃」的返回值。

实测确认的两条：

1. `.github/workflows/release.yml` 的「校验元数据能被客户端解析」跑
   `:core:test --tests com.hgtv.star.core.AppUpdatesTest`，而 `AppUpdates` 全仓已不存在

2. `data/PlaybackTransport.kt:69` 与 `:78` 重复 `addInterceptor(SessionInterceptor())`
   → 播放链路每个响应 `peekBody(32KB)` 跑两遍，在首帧关键路径上。

评审主结论：工程质量本身很高（基线 profile、首块 512KB、索引落盘、R8 剥日志、279 单测），
但复杂度已超出单体 Activity 上限——`MainActivity` 家族 23 文件 15,384 行、297 个可写字段、
七套手工"代际号"（generation / playbackSession / watchdogSession / failureHandledSession /
danmakuToken / accountToken / recommendToken）、22 个线程池、0 协程、app 层 0 测试。

其他重点：API<22 跳过证书链校验（但内置 G2 根已备好，可改单锚）；会话凭证明文写
`/sdcard/.hgtv/`（targetSdk 29 + requestLegacyExternalStorage）；播放进度每 5s 把 200 条历史
全量序列化 + SharedPreferences 整文件 commit（约 288MB/小时写入）；无 onSaveInstanceState；
无 WAKE_LOCK/WifiLock；ExoPlayer 2.19.1 / OkHttp 3.12.13 均 EOL；无字幕/音轨选择。

## 架构重构落地（分支 arch/v2-rebuild，commit c8359ba）

按用户要求「除 P0-2 / P0-3 / P2-5 外全修」，产出 `docs/架构重构说明.md`。

**关键版本约束（以后别再踩）**：Media3 从 **1.5.0 起要求 minSdk 21**，
1.4.1 是最后一个支持 Android 4.4 的版本。实测 AAR 清单：1.3.1/1.4.1 → 19，
1.5.1/1.6.1 → 21。要再升必须先抬 minSdk。

落地内容：
- `core/WorkLanes.kt`：5 条命名车道 net4/fanout6/player2/danmaku1/disk1，同时暴露
  executor 与 dispatcher；MainActivity 7 个池 + ContentRepository 4 个池全部收敛。
  线程池改为**进程级**，`onDestroy` 只 `appScope.cancel()`，不再 shutdownNow。
- `core/playback/PlaybackState.kt` + `PlaybackMachine.kt`：纯函数状态机，5 条迁移规则，
  15 个单测（`PlaybackMachineTest`）。`app/architecture/PlaybackController.kt` 持 StateFlow。
  `playbackSession`/`playbackReady`/`playError` 改成只读投影，两处 `++` 合并为 `beginSession()`。
- `data/ProgressStore.kt`：进度一剧一文件，写放大 O(200)→O(1)，间隔 5s→15s，带一次性迁移。
- Media3 1.4.1 / OkHttp 4.12.0 / coroutines 1.8.1；`-opt-in=UnstableApi`。
- 电源：`PlaybackPower`（WifiLock）+ `setWakeMode`（在 configurePlayer，主线程）。
- 恢复：`onSaveInstanceState` 存 6 个值，按 seriesId 从本机历史反查 Series。
- 界面：手机/平板 960×540 画布（电视仍 1280×720）、电视纵向过扫描 +24dp、按钮补 contentDescription。

**踩过的两个坑**：
1. OkHttp 4 里 `Call.request()` / `Chain.request()` 仍是**方法**，只有 `Response.request` 是属性；
   批量脚本统一改成属性会编译失败。
2. `beginSession()` 必须同时 `_state.update { copy(sessionId = id) }`，否则 `playbackSession`
   投影读旧值，「作废旧回调」失效。

**明确不采用**（理由写进文档 §6）：Tunneling（要求 SurfaceView，会破坏竖屏全屏的 TextureView
变换）、异步 MediaCodec（廉价盒子故障率高）、字幕（平台不下发）。

验证：assembleDebug / assembleRelease / core:test 全通过；release 2.34MB → 2.48MB（+148KB）。
未做真机验证，回归清单在文档 §12。未改版本号、未推送。

## 真机崩溃修复（commit 8295e43）

设备：S905L3B / Android 9，adb `192.168.31.121:5555`（**已 root，uid=0**）。
`dataDir=/data/user_de/0/com.hgtv.star`（direct-boot aware，不是 `/data/data/`）。

崩溃：

```
InflateException: Error inflating class com.google.android.exoplayer2.ui.PlayerView
Caused by: ClassNotFoundException
  at MainActivityPlayerKt.playEpisode(MainActivityPlayer.kt:720)
```

**根因**：Media3 迁移脚本只扫 `kotlin/` 下的 `.kt`，漏了
`res/layout/player_surface_texture.xml` 里写死的类名。XML 类名是字符串，
编译期查不出来；只有「竖屏短剧全屏」打开且形态判定为手机/平板时才 inflate 这份布局，
所以是特定开关才触发的崩溃。

**连带发现**：`baseline-prof.txt` 里 62 行 `com/google/android/exoplayer2/**` 迁移后
全部不存在，ART 静默跳过 → 冷启动 AOT 对播放链路完全失效。已按包名映射 + 逐类核对
Media3 jar（56 迁移 / 6 剔除），现 551 行、0 处 exoplayer2。

**以后换播放内核时的检查清单**：
1. `grep -rn "com.google.android.exoplayer2" android/app/src/main/res`（XML 类名）
2. `AndroidManifest` 里的类名
3. `baseline-prof.txt` 的类清单
4. `proguard-rules.pro` 的 keep 规则

真机验证通过：起播正常、崩溃缓冲 0 条、pid 稳定、进度文件落地 4 个 json、
旧 `progress` 键已从 shared_prefs 移除。用户复测确认不崩了。

## 卡片季号 + 扫码登录（commit 23fe686）

用户要求：卡片没显示「第 x 季」就默认「第 1 季」。改 `SeriesSeasons.badge(series)`
不再对单季返回空串，一律返回「第 N 季」；`MainActivityHome` 顶部信息区复用同一口径。

随后用户报「二维码登录无法显示二维码，connection closed by peer」。排查过程：

- 本机用同一份 OkHttp 4 + `HgtvTls` 打 `api5-normal-lq.fqnovel.com` 的出码端点，
  **裸 client / HgtvTls / 含 h2 三种配置全部 200** → 不是 TLS 参数问题。
- 设备侧：DNS 通、ping 通、TCP 443 可连；但**全局 IPv6 地址存在而 `ip -6 route` 为空**，
  应用 DNS 缓存把 6 条 IPv6 排在前面（这是个隐患，但不是本次原因）。
- 真正原因在代码：`git diff` 基线发现迁移把
  `HttpUrl.parse(HOST+path)` 改成了 `HOST+path.toHttpUrlOrNull()`，**括号丢了**。
  `path` 是相对路径 → null → `HOST+null` = `https://api5-normal-lq.fqnovel.comnull`。

已修 `(HOST + path)`，抽出 `QrLogin.endpoint()` 并加 `QrLoginUrlTest`（4 个用例）。
用户复测二维码正常显示。

**未处理的隐患**：这台盒子有 IPv6 地址但没有 IPv6 默认路由，`HgtvDns` 仍会缓存
AAAA 记录并排在 A 记录前面。目前靠 OkHttp 逐地址回退能兜住，但如果某天出现
「连接很慢才成功」，优先查这里。
