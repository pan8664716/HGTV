# 2026-10-30

## 播放地址窗口期统一为 10 分钟（commit 9751323）

现场：用户反馈「播几集后按下一集 → 地址过期：播放地址已失效（HTTP 403）」，
退出播放页再进就好了。

### 根因

持有播放地址的路径有三条，有效期各自为政，其中两条**取用时根本不校验**：

| 路径 | 改前 | 改后 |
| --- | --- | --- |
| 内存 `streamCache`（8 条） | 2 分钟 | 10 分钟 |
| 落盘 `PlaybackCache` | 20 分钟 | 10 分钟 |
| 队列项 `queuedVideo` | 只记 `queuedAt`，**不校验** | 10 分钟，超龄摘掉重取 |
| 推荐页 `recommendPrepared` | 只记 `recommendPreparedAt`，**不校验** | 10 分钟，超龄关掉重取 |

2 分钟 / 20 分钟那组还有个隐性错误：2 分钟一到内存失效，紧接着又命中落盘那份 20 分钟的
地址——「更短」只是多一次读盘，没让起播更安全。

### 做法

- 唯一一处定义：`PlaybackCache.URL_FRESH_MS = 10*60*1000L`
- `PREPARED_FRESH_MS = URL_FRESH_MS`、`ContentRepository.STREAM_CACHE_MS = PlaybackCache.URL_FRESH_MS`
- `PreparedSlot` 保留 2 分钟（更严格；10 分钟是**上限**不是目标值）
- `maybeQueueNext` 每 tick 检查队列项年龄，超龄 `dropQueuedEpisode()` 让下一次重新预热
- `playEpisode` 的 `fromQueue` 加 `isPreparedFresh(queuedAt)` 条件
- `startRecommendEpisode` 取预热前校验 `recommendPreparedAt`，过期当场 `close()`

测试：`PreparedFreshnessTest` 加了「窗口是 10 分钟」「两层同一数字」两个断言——
改窗口必须同时改用例。

### 缓存层级的实际数字（用户问过，记住）

- **正片只往后预热 1 集**（片尾约 30 秒窗口），`preparedNext` 单槽 2 分钟，队列 1 项。
- **推荐页往后 3~4 部 + 往回 2 部**（连续同向滑 ≥3 次扩到 4），最多保留 6 份预热首集
  （`RECOMMEND_PREPARED_LIMIT=6`）；深度分级：第 1 部完整、第 2 部元数据、其余只取地址。
- 落盘地址缓存最多 80 个文件 / 48MB。

### 注意

- 用户自己在 `9ee7a75` 打了 `v1.2.9` tag，本次修复在 tag **之后**，1.2.9 不含此修复。
- 真机测试设备已从 S905L3B 盒子换成 `127.0.0.1:16384`（PGT-AN00 / Honor / Android 12）。
  该机 TLS 支持到 1.3（盒子只到 1.2）。
- 上次 35 秒的 debug 日志没复现 403：4 次换集全是手动，`Next episode prepared/queued` 0 条，
  预热/队列那条路根本没走。复现需要「连续自动播放」或「片尾暂停 10 分钟以上」。

## 403 为什么自愈救不回来（commit acac79d）

用户追问「403 不是有降级策略吗，为什么还会报错」。查下来是**队列项走的是另一条分支，
绕过了清地址**：

```
① 队列项（第 N+1 集）预加载读到 403
② playerFailure 进队列分支，第一件事就是 dropQueuedEpisode()
   → queuedEpisodeId 被清成 null
③ 走 restartAnotherEpisode(N+1) 重切，但**没人清过 N+1 的地址**
④ stream(N+1) 原样命中内存里那条坏地址 → 又 403
⑤ autoNextFailures 已用满 → 落错误页
⑥ 退出播放页 → 内存缓存被清 → 重新取地址 → 好了
```

关键点：`dropQueuedEpisode()` 在 `failingEpisode = queuedEpisodeId ?: expiredEpisode`
之前执行，所以后面的自愈分支算出来的 `failingEpisode` 是**当前集**——清错对象。

### 修复

- `PlaybackCache.urlFile()` 文件名改成 `url-<集id>-<sha1>.bin`（原来只有 sha1，
  哈希后无法按集匹配）
- 新增 `PlaybackCache.invalidateUrlById(id)`：按集删所有档位
- 新增 `ContentRepository.forgetStreamAllQualities(id)`：内存按 `集:` 前缀清 + 落盘按集清
  + `rotateDeviceForRetry()`
- `playerFailure` 队列分支：在 `dropQueuedEpisode()` **之前**抄 `failedQueuedId`，
  地址类失败时作废地址 / 索引 / 传输

**为什么按集整体作废**：预取时的上限与 `device_level` 可能已被降档改过，
精确键（`集:上限:档位`）算不出来，用错键等于什么都没删。

测试：`PlaybackCacheUrlByIdTest` 4 个用例，含「删 111 不误伤 1111」。

### 修正（commit 880e9ed）——上一轮判断有误

**我当时说错了**：`playerFailure` 里自愈分支（612 行）在队列分支（689 行）**之前**，
且 611 行 `failingEpisode = queuedEpisodeId ?: expiredEpisode` 取的时候
`queuedEpisodeId` 还没被清。所以**不存在「清错对象」**，自愈本来就用对了集。

我把「按集作废」加在队列分支，那里对 403 是**死代码**（自愈已经 return 了）。
已删除，并把自愈分支里的 `forgetStream(集, 上限)` 换成 `forgetStreamAllQualities(集)`——
精确键 `集:上限:device_level` 里的上限/档位是**预取那一刻**的值，期间降档或
`device_level` 变化会让键对不上，等于什么都没删。

**教训**：读一个 400 行的 `playerFailure` 时，先确认分支的**执行顺序**再下结论。
我看到「dropQueuedEpisode 清空 queuedEpisodeId」就推断后面会算错，
但没注意到自愈分支在它之前。这类「顺序假设」错误在长函数里特别容易发生。

### 真正的根因（commit 155c8e0）

排除法确定：退出播放页会清掉 `queuedVideo` / `preparedNext` / `recommendPrepared` /
`sessionPlayback` 降级状态，但**不清** `streamCache` 与 `PlaybackCache`。
既然「退出再进就好」，坏状态必然在被清掉的那一组里——也就是**预热持有物**。

而 `stream()` 的命中条件是键完全相同：键相同则 `forgetStream` 能删对，键不同则查不到，
**两种情况都会重新取地址**。所以坏地址不可能来自 `streamCache` / 落盘缓存，
只可能来自预热持有物（它们持有 `RemoteVideo` 实例，不查缓存）。

**最终链条**（每一环都有代码依据）：

```
① 片尾前 30 秒预热下一集 → 挂进播放列表
② Media3 后台预加载它 → 读到 403（预热那份地址已过期）
③ 自愈分支 failingEpisode = queuedEpisodeId = 下一集
   → streamRetried["下一集:档位"] 被记上
   → 用户还没开始看这一集，额度已经没了
④ 自愈重切 → restartAnotherEpisode → onEpisodeSwitch（不清 streamRetries）
⑤ 下一集再撞 403 → 额度已用 → 错误页
⑥ 退出播放页 → 换集走 onEpisodeStart → 额度清空 → 又能自愈一次 → 好了
```

**修法**：判据 `queuedNearEnd`——队列项在片尾之外报错说明当前集还在正常播，
IO 只可能来自后台预加载，这种情况救回来即可，**不记账**。
有界性：自愈会 `dropQueuedEpisode()`，重来后 `queuedEpisodeId` 为空，
下一次失败走正常额度判断，最多「预加载救一次 + 正式播放救一次」。

**为什么之前没看出来**：`streamRetries` 的键是 `"集:档位"`，但「哪一次失败」没有进键。
预加载失败和正式播放失败共用同一份额度，而预加载发生在用户看不见的后台。

  三个 ExoPlayer 都还在，进播放页就听到两条音轨。现在 `onHidden()` 直接
  `release()` 播放器 + 关闭 `RemoteVideo`；`onShown()` 按 `playingIndex` 重建。
  另外 `PhoneMainActivity.onPause/onResume` 通知推荐页，选集跳转前也先 `onHidden()`。
- 验证：播放页实测标签五个独立、无「展开」、信息区贴底；推荐页的 dump 因视频一直在动
  （`could not get idle state`）没抓到，需要真机确认。

## 手机端第八轮：续播 + 播放页手势 + 全屏 UI

**续播（推荐页）**
- `PhoneFeedView.playIndex()` 先读 `library.progress(series.id)`，按 `episodeId` 定位到那一集，
  再 `seekTo(position)`；同时新增 `startSaveTicker()` 每 5 秒落盘。
- 之前信息流固定播第一集、且从不存进度，所以「推荐页 → 播放页 → 返回」每次都是从头。

**播放页手势**（`PhonePlayerActivity`，用 `GestureDetector` + 一层全屏 `View` 接管触摸）
- 单击：竖屏暂停/继续；全屏显示/隐藏控件
- 双击：暂停/继续
- 长按左/右 1/3：临时 2 倍速（`ACTION_UP` 恢复 `userSpeed`）
- 长按中间 1/3：播放设置
- 横向滑动（仅全屏）：拖进度，`dx / 屏宽 * duration * 1.2`

**全屏 UI**
- 顶部：返回 + 「剧名｜第N集」+ 三个点（打开播放设置）
- 底部：SeekBar + 时间 + 倍速/选集/全屏三个胶囊
- 进全屏默认全隐藏（`chromeVisible=true` 再 `toggleChrome()` 取反）

**播放设置**：倍速 / 弹幕显示方式 / 弹幕大小 / 画面缩放，与 TV 的 `Library` 偏好同一份数据；
全屏时从右侧出（宽 62%），竖屏时从底部出。

**注意**：`Activity` 里没有 `width`，手势里要用 `root.width` 兜底 `displayMetrics.widthPixels`。

## 手机端第九轮：长按阈值 / 全屏默认隐藏 / 底部重排

- **长按改 800ms**：`GestureDetector` 的 500ms 无法配置，改成自己用 `Handler.postDelayed`
  计时，并 `gesture.setIsLongpressEnabled(false)`。手指移动超过 `scaledTouchSlop` 就撤销。
  500ms 太短——用户「点一下」稍慢就弹设置，这是「点击屏幕中间显示了播放设置」的根因。
- **全屏默认隐藏**：`chromeVisible = false` + `applyChrome()`（原来 `true` 再 `toggleChrome()`，
  逻辑对但容易被后续改动破坏，改成显式状态 + 单一应用函数）。
- **播放页关掉视频页的信息栏**（`page.setInfoVisible(false)`）：底部「倍速/选集/全屏」
  与「观看完整短剧」重叠，就是因为两套底部 UI 同时存在。
- 进度条右侧显示百分比（`permille / 10`），左侧仍是时间。
- 播放设置面板：`WRAP_CONTENT` 高度、全屏时宽 52% 右侧居中、背景 `0xE61E2228` 半透明，
  遮罩降到 `0x4D000000`。

## 手机端第十轮：信息流全屏按钮接通

- 根因：`PhoneFeedView` 创建 `PhoneVideoPage` 时只接了 `onTogglePlay` / `onEpisodeClick`，
  **`onFullscreen` 从来没赋值**，按钮点了当然没反应。
- 现在点全屏 → `onHidden()`（停信息流解码器）→ 启动 `PhonePlayerActivity` 并带
  `EXTRA_FULLSCREEN=true`；播放页在 `attach()` 挂上解码器之后 `root.post { toggleFullscreen() }`，
  避免黑屏旋转。
- 实测：点全屏 → `cur=1920x1080` + 前台 `PhonePlayerActivity`；返回 → 恢复 `1080x1920`
  + 回 `PhoneMainActivity`，无崩溃。

## 手机端第十一轮：单播放器 + 手势不再吃按钮

**根因：手势层是一整块全屏 View，压在最上面**
- 它把「观看完整短剧」「选集」这些按钮的点击全吃了 → 按钮点了没反应；
- 点按钮的时长超过长按阈值 → 被判成长按 → 弹出播放设置。
- 改法：**删掉这层 View**，手势挂到 `page.setOnTouchListener` 上并返回 false。
  Android 的事件分发是「子 View 先消费」，所以点按钮时这里根本收不到，只有点空白才走手势。

**进程级单播放器**（`PhoneServices.player()`）
- 之前：信息流三个体裁各一个 + 播放页一个 = 4 个 `ExoPlayer`，各记各的状态，
  于是「切页后另一条流还在响」「进播放页从头开始」「偶发状态错乱」。
- 现在：全进程一个 `@Volatile ExoPlayer`，各页面只绑/解 `PlayerView`（`PhoneServices.detach()`），
  **切页不再 release**（release 了别的页面就用不了）。
- 验证：`logcat | grep -c 'ExoPlayerImpl: Init'` = **1**。

**播放页底部**
- 恢复视频页的信息栏（含「观看完整短剧」按钮）；
- 播放页把按钮文案换成「选集 全N集｜第N集」（`bind(..., watchText = ...)`）；
- 去掉底部栏里「倍速 / 选集 / 全屏」三个胶囊——它们和那条按钮叠在一起。倍速与画面缩放在三个点里。

## 手机端第十二轮：单击去抖 + 进度条让位

- **「点一下暂停又播放」**：单击被处理了两次——`PhoneVideoPage` 的 `setOnClickListener`
  和 `GestureDetector.onSingleTapConfirmed` 都调了 toggle。去掉手势里的那份，
  只留 `page.onTogglePlay`，并加 250ms 去抖（双击在 Android 上是两次完整点击，
  不去抖会连切三次）。
- **进度条压在选集按钮上**：`bottomBar` 和视频页信息栏都在 `Gravity.BOTTOM`。
  信息栏高度随标签 / 集数变化，不能写死，改成 `PhoneVideoPage.infoHeight()` 读实测值，
  在 `bind` 之后 `root.post { bottomMargin = infoHeight() }` 抬上去。
- 验证：`ExoPlayerImpl: Init` 仍为 1，无崩溃；底部布局 dump 抓不到（视频在播）。

## 手机端第十三轮：按交互规范重写手势（状态机）

**四态状态机**（`TouchMode`：IDLE / PRESSING / LONG_PRESSED / DRAGGING）
- 优先级由状态迁移保证，不再堆监听器：
  - 横滑（仅全屏）→ DRAGGING，进入后不再判长按
  - 长按 500ms 无位移 → LONG_PRESSED（全屏任意区域 = 2 倍速；非全屏中间 1/3 = 设置，左右 1/3 = 2 倍速）
  - UP 后等 300ms 双击窗口：有第二次点击 → 双击（播放/暂停）；没有 → 单击
  - 单击：全屏 = 显隐界面；非全屏 = 播放/暂停
- 拖进度：`seekFrom + dx/屏宽 * duration * 1.2`，过程中显示目标时间预览，UP 才 seek。
- 关键坑：`onTouchEvent` 与 `Activity` 同名成员冲突 → 改名 `handleTouch`。

**播放设置按 TV 的 `buildPlaybackMenu` 顺序**
倍速 → 画面模式 → 弹幕 → 弹幕速度 → 弹幕大小 → 弹幕透明度（→ 画面缩放）
清晰度（要重新取流）、定时（会话计时）、解码（要重建播放器）**还没接**。

**底部栏**：进度条 + 时间/百分比 + 倍速/选集/全屏三个胶囊（抬到视频页信息栏上方，
`bottomMargin = page.infoHeight()`）。
